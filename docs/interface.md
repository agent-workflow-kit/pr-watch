# pr-watch: interface

Status: implemented, pre-1.0 (current version 0.25.0). This document is the single normative source for pr-watch's rules. `design.md` records the decisions and the internal structure and links to the headings here instead of restating them; the README, the architecture and the schemas follow it. Machine-readable shapes are in `schemas/`.

## Concepts

pr-watch turns "what changed on these PRs since I last looked?" into a stream of events. A tool or a person registers **watches** on pull requests (GitHub) or merge requests (GitLab), a periodic `poll` compares what the host reports now with what it reported last time, and every difference becomes an **event** that consumers read with their own cursor or receive through an `on-<event>` hook. pr-watch reads the host only through forgectl, never posts or changes anything on a host, and takes no external action, so it keeps no audit log. Terms defined later are used earlier in places: Poll cycle, Digest, State, Events, Pacing and backoff, Residual risks.

### Identifiers

- **Repo id** and **PR reference:** as in the design guide, section 4.1. `host/<full project path>` for a repo; a PR is a URL or `host/<full project path>#N` (GitLab numbers written without `!`); output always uses `#N`. pr-watch validates every user value before it builds argv: a PR argument must match the `pr` pattern of `schemas/defs.json` (an uppercase or mixed-case host is accepted and lowercased; the schema pattern is the canonical, lowercase-host form of stored and printed values) or be an `https://` URL (grammar under Reference resolution); `--host` must match the host grammar and `--repo` the repo-id grammar (exit 2 `usage` at `watch add` and `poll`); every stored `pr` and filter is re-validated before use; shas for `compare` match `^[0-9a-f]{40}$`. argv is built as `--option=value` where forgectl accepts it; a `--` before positionals is used only if confirmed (a forgectl question, see design.md Live verification), so validation is the primary defense. A stored free string is never put in argv; `pr_id` is never used in argv or a path. forgectl's grammar decides everything else (an invalid reference is exit 2, `code: invalid_pr`).
- **Leading `-`, `.git`, length:** a PR reference, URL or `--repo` whose first path segment starts with `-` is refused. A later segment that starts with `-` is refused too, except the repo name of a path of exactly two segments on a host other than `gitlab.com` (a GitHub repo name may start with `-`, so `github.com/o/-r#1` is accepted; the backend is known only after config, so a later stage refuses it where the backend does not allow it). This is safe because the canonical argv token starts with the host, never with `-`. A path whose last segment ends in `.git` is refused: a deliberate narrowing of the `repo_id` and `pr` patterns of `schemas/defs.json`, which forgectl does not refuse either. `host/path` (the whole repo id, in a `--repo` value or in a PR reference) is at most 255 characters and at most 20 path segments.
- **Host normalization:** a `--host` value, the host of a repo id and the host of a URL are ASCII, lowercased, labels at most 63 characters, the name at most 253; a port is 1 to 65535 without a leading zero; `:443` is dropped (forgectl does the same) and a `www.` prefix is dropped for `github.com` and `gitlab.com` (without a port). The normalized form is what is stored, printed and matched, so config `hosts:` and `repos:` keys must be written in the normalized form (a key written `www.github.com` or `github.com:443` never matches).
- **Refusal kinds:** every refused value is exit 2 with `details.kind`: `bad_pr` (code `invalid_pr`), and, with code `usage`: `bad_host`, `bad_repo`, `bad_owner`, `bad_label`, `bad_cursor`, `bad_limit`, `bad_type`, `bad_duration`, `bad_every`, `bad_hook`, `bad_watch_id`, `ambiguous_reference` (a reference matches more than one stored PR), `bad_combination` (an invalid mix of options, including a `--repo` whose host is not in the given `--host` list), `owner_required`, `filters_too_long` (the watch key of the `--host` and `--repo` filters would pass 4096 characters), `missing_target`, `missing_labels`, `too_many_labels` (a `label add` that would leave a watch with more than 64 labels; `details.limit` and `details.count` hold the limit and the count it would reach), `conflicting_flags` (Global flags), and, for `cron`, `malformed_crontab` (the crontab holds a block that is not exactly one start line followed by one end line) and `unsafe_path` (the path of `pr-watch`, or a `PATH=` or entry line, that cannot be written to a crontab). Messages are fixed text and never echo the value.
- **`pr_id`:** the opaque, stable id forgectl reports for a PR (it survives repository renames and moves). pr-watch keys every stored PR on `pr_id` and prints the canonical `pr` form beside it; the `pr` form is refreshed on every successful snapshot. A reference that now names a different `pr_id` than the stored one (a number reused after a repo was deleted and recreated) is a different PR.
- **Reference resolution:** `watch add` and `poll --pr` accept a `pr` reference (`host/path#N`) or a URL; `show`, `list --pr`, `events --pr`, `export --pr`, `watch remove` and `label` accept a `pr` reference, a URL or a `pr_id`. A name or URL that matches more than one stored row (a repo name that was reused) is exit 2 `usage` with the hint to use the `pr_id`; `watch add` with such a name takes the `pr_id` from its snapshot. Matching a reference against the stored canonical `pr` and `pr_id` happens offline in process and is case-insensitive in host and path (the stored form is the lowercase host and the path as forgectl printed it). A URL is parsed by a small pattern that follows forgectl v0.55.3: the scheme is exactly `https://` (lowercase; `HTTPS://` is `invalid_pr`), the host is case-insensitive, and userinfo, `%`, `\`, whitespace and non-ASCII characters are refused. GitHub form: `https://<host>/<owner>/<repo>/pull/<N>`, optionally followed by one of `/files`, `/commits`, `/commits/<7 to 40 hex digits>`, `/checks`, `.diff` or `.patch`. GitLab form: `https://<host>/<path>/merge_requests/<N>` with `/-` before `merge_requests` optional, optionally followed by one of `/diffs`, `/commits` or `/pipelines`. One trailing slash is accepted; a query and a fragment made of `[A-Za-z0-9._~=&-]` are dropped. Any other trailing path is `invalid_pr`, as is a GitLab `api_prefix` host or any form the parser does not recognize (with the hint to use `host/path#N`). On `github.com` and `gitlab.com` the URL kind must match the host (`pull` on GitHub, `merge_requests` on GitLab); other hosts accept either form. There are no stored aliases, so a stale name after a repo rename does not match a row (use the new name or the `pr_id`). `poll --pr` resolves the reference offline and then snapshots (it does contact the host); `show`, `list`, `events`, `export`, `watch remove` and `label` never contact a host.
- **Owner:** `^[a-z0-9][a-z0-9_.:@-]{0,63}$`, a free string naming who holds a reference to a watch (for example `review-respond`, `human:<name>`). pr-watch assigns no meaning to an owner. `watch add`, `watch remove`, `label add` and `label remove` take `--owner O`. Without it: on a TTY the owner is `human:<me.name>`; when stdin is not a TTY the command exits 2 before the config is read (`usage`, `details.kind: owner_required`, message "--owner is required when not run from a terminal"). `me.name` defaults to the OS user name; cleaning follows the design guide section 6 actor rule (ASCII-only lowercase: non-ASCII characters are not case-mapped and become `-`; characters outside the owner charset replaced with `-`; a leading non-alphanumeric stripped; cut to 58 characters so that `human:<name>` is at most 64); an owner given with `--owner` is never cleaned. This differs from the design guide's actor rule on purpose (the guide replaces with `_` and does not lowercase; the owner grammar here is lowercase only); an empty result is exit 2 asking for `--owner`.
- **Watch key:** a per-PR watch is keyed by `pr_id`. A query watch is keyed by its canonical query string: `mine+open` followed, when filters were given, by `;host=<h>,...;repo=<id>,...` with each list sorted and deduplicated; repo ids are ASCII-lowercased first (`h/O/R` and `h/o/r` are one key), and a key longer than 4096 characters is exit 2 `usage` (`details.kind: filters_too_long`). Two `watch add` calls with the same key are the same watch.
- **Watch id:** `w-` followed by 10 lowercase base32 characters (`a-z`, `2-7`), generated once when a watch is created. Printed by `watch add` and `list`; not needed to remove a watch (a watch is removed by its reference or query).
- **Event id:** `ev-` followed by 12 lowercase base32 characters, generated when the event is stored. It is the deduplication key for hook consumers.
- **Cursor:** `v1.<store_id>.<seq>`: `store_id` is 8 lowercase base32 characters created once with `state.db`, and `seq` is a non-negative decimal integer, the event stream position. A cursor is opaque to consumers (they store and return it verbatim). The grammar is `^v1\.[a-z2-7]{8}\.[0-9]{1,18}$`.
- **Label:** `key=value`; the key matches `^[a-z][a-z0-9_-]{0,31}$` and the value `^[A-Za-z0-9._:@/#+-]{1,128}$` (design guide section 9; no key has built-in meaning).
- **Time:** every stored and printed timestamp is UTC as `YYYY-MM-DDTHH:MM:SS.ffffffZ`. Timestamps read from forgectl are converted to that form. `--since`-style durations take `0` or an integer and a unit: `ms`, `s`, `m`, `h`, `d`.

### Watches, owners and members

- A **per-PR watch** follows one PR. `watch add <pr>` resolves it and records the watch.
- A **query watch** follows a query. Version 0.x has one query, `--mine --open`: the PRs authored by the account forgectl calls "me" on each host in scope. The optional `--host <host>` and `--repo <id>` filters (both repeatable) narrow it and become part of its key. A query's members are the listed items that match its filters: the `--host` list (OR), the `--repo` list (OR), the two lists ANDed; a repo implies its host (a `--repo` whose host is not in the `--host` list is exit 2 `usage` at `watch add`). Hosts in scope are those `forgectl whoami` lists with `token_source` other than `none`; a declared host with `none` is reported `skipped: no_credential`; a per-PR watch's host is always attempted. pr-watch caches the host list for `hosts_ttl` (default 1 hour).
- Every watch has a set of **owners** and a set of **labels**. A label belongs to the (watch, owner) pair that added it and is removed with that owner's reference; the labels of a watch are the union over its owners; adding an owner or a label that is already present is a no-op. `watch remove` removes only the named owner's reference (and its labels); the watch ends when its last owner is gone. An event's labels are the union over every watch that includes the PR, as they were at detection; a label added later does not reach stored events.
- A query watch has **members**: the PRs its open listing found. A member is a PR row (State) with a `sources` row for the query watch; a PR can be a member of several query watches and the subject of a per-PR watch at once, with one row, one digest and one event stream. Enumeration only adds: a listed open item that matches the filters becomes a member (a row with no digest, to be baselined silently by its first snapshot) and sets that source's `left_count` to 0. A member of a host that is absent from a **complete** open listing of that host gets `sources.left_count` + 1; a source with `left_count` 2 (absent from two consecutive complete listings, so one lagging search result does not remove a member) is a snapshot trigger (Poll cycle, step 4 (d)); an incomplete listing changes no `left_count`. A source is removed only inside the snapshot commit (Locks and commit): when the snapshot shows the PR `open` and its source has `left_count` 2, that query's source is deleted (no event; the row is dropped when no source remains); when the snapshot shows `merged` or `closed` the sources stay until expiry, so the `merged` or `closed` event is always stored. A snapshot that fails (`not_found` and the rest) keeps the source.
- A PR row is dropped, in the same transaction that removes its last source, when none of its sources remains (all its per-PR watches were removed and it is no longer a member of any query watch that still exists). Its stored events stay until retention.

### PR status

Each stored PR has a status:

- `active`: polled normally.
- `terminal`: seen `merged` (final) or `closed`. `terminal_at` is the local time the snapshot that saw the PR terminal was committed (a PR merged long before `watch add` gets the full `expiry.after_terminal` from first sight). A closed PR keeps its row (digest included) for `expiry.after_terminal` after `terminal_at`. When an enumeration lists a closed PR's row as `open` (the query's open listing, or a per-PR repo listing), the PR is reactivated: `status` becomes `active`, `terminal_at` is cleared and `rebaseline` is set; its next snapshot replaces the digest and emits only `reopened`, `pushed` (when the head changed), `merged` or `closed`, and comments, reviews and CI changes made while it was closed are not reported. Repos that hold a terminal-closed per-PR PR inside the expiry stay in the per-PR listing step of the Poll cycle. A terminal PR gets no snapshots and is never `unreachable`.
- `unreachable`: `failures.unreachable_after` consecutive counted per-PR failures (Failures). Snapshotted only on its host's full pass, and it clears on the first success. Whole-host failures never change PR status. An `unreachable` PR never expires by itself (a deleted repo stays visible until its watch is removed, `list --status unreachable` shows it, and `post-poll` named it once); it costs one snapshot per full pass.

A terminal PR's row (digest included) is deleted `expiry.after_terminal` after `terminal_at`, and so are the watches that only referred to them (a per-PR watch ends; a member is dropped). The deletion happens in `prune` (so up to a day after the expiry). The expiry predicate (`terminal_at` older than `expiry.after_terminal`) is evaluated inside the transaction that deletes the row, in `prune` per row and in `watch add`: `watch add` of a PR whose row satisfies it treats the row as absent, deletes it and baselines the PR as new in one transaction (so a re-add never lands on a row `prune` is about to delete).

### Untrusted text

pr-watch stores and prints no free text from a host: no comment body, title, description or check output. The only host text it handles is one-line: a login, a file path, a check name and a `blocked_by.detail`. forgectl has already replaced control characters and bidi marks in them with `<U+XXXX>` markers; pr-watch passes them through, marks them `x-untrusted` in the schemas, and never puts them in argv or environment variables (hooks receive them on stdin only). Anything that needs the text reads it through forgectl by id (`comments`, `reviews`). Consumers must treat the login, path, check-name and detail fields as untrusted. The one other host text that can appear is the `message` of an error (the error envelope, `lower_error.message`, `log.jsonl` messages); it is forgectl's sanitized one-line text, truncated to 256 characters and marked `x-untrusted` in the schemas, and it is never put in argv or environment.

Every host-derived one-line field (login, path, check name, `blocked_by.detail`) is truncated to 256 characters at a marker boundary (never inside a `<U+XXXX>` marker) with a trailing `...` kept inside the limit, before it is stored or validated (keys and `seen` are computed from the full sanitized value first); truncation never fails a snapshot or a commit; keys and `seen` use ids and hashes of the full value, so truncated values cannot collide into one check. A truncated `path` is not usable for matching. A marker `<U+XXXX>` is not proof that a character was removed (an author can type it); consumers match check names exactly with forgectl's `required` flag and never by substring. The CLI's human output replaces any remaining C0, C1 or ESC character in every host-derived string (defense in depth).

## Detection

### Poll cycle

`poll` is the only command that contacts a host. Cron or a caller runs it; `events`, `list`, `show` and `watch` never do, except the per-PR `watch add`'s baseline (see `watch add`). One cycle:

1. **Preflight.** Resolve forgectl once (absolute `PATH` entries only), check its version, load the host list (`whoami`, cached `hosts_ttl`) (Failures).
2. **Enumerate, one host at a time.** (a) Query watches: for every host in scope that some query applies to, one `forgectl prs --host <h> --author me --state open --limit 1000 --json`. `--repo` filters are applied client-side to the host's list (forgectl rejects `--repo` with `--host`, so no `--author me --repo` call is made). A listing with `complete: false` (more than 1000 open PRs, or a cut) is processed for the PRs it lists, reported as `hosts.<h>.incomplete_listing: true`, and never used to conclude that a member left the set. (b) Per-PR watches: for every repo that has a per-PR watch whose PR is `active` or terminal-closed inside `expiry.after_terminal`, one `forgectl prs --repo <id> --state all --updated-since <w> --limit 1000 --json`, where `w` is the repo scope's `watermark` minus `poll.overlap`. The `scopes` row for a repo is created by the first listing: while it does not exist, `w` is the smallest `snap_updated_at` among the repo's `active` or closed-inside-expiry per-PR rows that have a digest (minus the overlap; a repo whose rows have no digest is not listed this cycle, trigger (a) covers them). Every listing writes the new watermark in its own transaction (State, transaction 1): the largest listed `updated_at` but never later than the poll's start (a PR listed with a future `updated_at` does not hide later changes; `listed_updated_at` keeps the listed value), or the old value when the listing is empty; a listing that failed writes nothing. A `complete: false` listing is safe to write because the same transaction marks every `active` per-PR row of that repo as changed (`listed_updated_at` becomes the larger of its value and `snap_updated_at` plus one microsecond), so trigger (b) snapshots them all and the marks survive a crash, deferral, a pause and low water. A `scopes` row is deleted by the first cycle in which no `active` or closed-inside-expiry per-PR row has that `repo` (a renamed repo's old row goes this way, and the new name starts as a new scope). Hosts are listed one at a time, never in one call; the snapshots of different hosts then run in parallel pools after all listings.
3. **Apply listings** (inside the transaction of each listing, State transaction 1). Items are matched to stored rows by `pr_id` only (an item whose `pr` equals a stored `pr` but whose `pr_id` differs is another PR and is ignored unless it makes a new member). For every listed item with a stored row: `listed_updated_at` becomes the larger of the old value and the item's `updated_at`, and the stored `pr` and `repo` are replaced by the item's. A listed open item that matches a query watch becomes a member or resets `left_count` (Watches, owners and members); a stored row that is `terminal` with kind `closed` and is listed `open` is reactivated (PR status). A listed item with no stored row that matches no query is ignored. Before inserting a source the transaction verifies that the watch still exists.
4. **Choose snapshots.** Only `active` rows are chosen by (a) to (e); only `unreachable` rows by (f); a `terminal` row is never chosen (a closed one becomes `active` first by reactivation). An eligible PR is snapshotted once per cycle when any of these holds: (a) it has no digest or `rebaseline` is set (a member just found, added with `--no-baseline`, or reopened); (b) `listed_updated_at` is greater than `snap_updated_at`; (c) it is unsettled (State) and `ci_stuck` is false; (d) one of its sources has `left_count` 2; (e) its host's full pass is in progress and the PR is not done for the pass (Pacing and backoff, Full pass); (f) it is `unreachable` and the same full-pass condition holds. Order: (b), (d), (a), (c), then (e), (f); while a pass is in progress with a (e) or (f) row waiting, group (c) takes at most three quarters of `poll.max_snapshots` per host; inside a group, oldest `last_polled_at` first. The cycle stops starting snapshots for a host after `poll.max_snapshots` of them (default 40; 0 means unlimited; `--full` ignores it) and for all hosts after `poll.max_duration` (default 15m, measured from the start of the poll cycle, before enumeration): the report has `truncated: true` and `deferred: n`; deferred PRs keep their triggers (all are persisted) and go first next cycle. `snap_updated_at` is set to the larger of the snapshot's `updated_at` and the `listed_updated_at` read when the snapshot started. A changed-PR mark is never separate from a successful commit: the triggers are persisted comparisons, so a failed or crashed snapshot is retried next cycle without any extra mark.
5. **Snapshot.** `forgectl snapshot <pr> --no-bodies --json` through a pool of `poll.concurrency` workers per host (Pacing and backoff), each PR under its own lease (Locks and commit). Each result is classified (Failures), then turned into a digest and diffed against the stored one (Digest, Events). `--no-bodies` leaves out the `body` of every review and every comment (thread comments included) and nothing else: the digest, the diff and every event payload read only ids, authors, states, shas, times, paths, lines and check fields, never a review or comment body, so no event field changes; the PR's own `body` stays. forgectl has had the flag since before `MIN_FORGECTL`, so there is no version branch. Every forgectl call has a wall-clock deadline of `forgectl.timeout` plus 10 seconds. The read loop stops at the output cap and at the deadline; the child's process group gets SIGTERM, then SIGKILL after 2 seconds, only while its leader is unreaped. The result is the local code `killed` (retryable per PR, Failures). `compare` has the same deadline. Before any diff the poll compares `snapshot.pr_id` with `prs.pr_id` (Failures, `pr_id_changed`).
6. **Commit.** All events and the new digest of one PR are stored in one compare-and-set transaction (Locks and commit); the sequence numbers are assigned inside it. A crash before commit loses nothing and repeats the work; after commit the events are durable.
7. **Hooks.** After each PR's commit, its `on-<event>` hooks are queued to a bounded pool inside the poll process (Hooks); the poll exits when the pool drains.
8. **Report and housekeeping.** The poll report is printed; `post-poll` fires when `failed` names a scope, a host or a PR that was not already `unreachable` at the start of the cycle, any `hosts.<h>.errors` is non-empty, or a PR became unreachable (its payload counts exclude itself; an already `unreachable` PR that fails again, or a PR that fails `too_large` while it is not yet unreachable, is in `failed` but never alone causes `post-poll`); `prune` work (retention, expiry, lease and scope cleanup, WAL checkpoint) runs at most once a day, at the end of any `poll` that ran to its end (not an interrupted one), when `meta.last_prune_at` is missing, unreadable, in the future or at least a day old; a failure of it never changes the poll's result.

A poll never writes to a host.

### Locks and commit

- A lease is per PR, taken when that PR's snapshot starts (not for all PRs up front) and released at its commit or failure. Row: holder pid, start time, boot id (`/proc/sys/kernel/random/boot_id`), expiry. Where `/proc` is unavailable (macOS) the start time and boot id are recorded as `unknown`, and such a holder counts as alive until its lease expires. The expiry is `3 x forgectl.timeout` (6 minutes by default), and never less than two forgectl calls of one worker (each up to the timeout plus 10 seconds, as the over-cap fallback makes two) plus 30 seconds; it is renewed after each forgectl call by the worker. A lease is taken over when its holder is dead (pid, start time and boot id do not verify) or it is expired, whether or not the holder is alive: takeover of a live holder is safe because every commit is a compare-and-set. Dead and expired leases are deleted by `prune`. A lease is not re-entrant: acquiring a lease that the same process (pid, start time and boot id) already holds returns none. An expiry that cannot be parsed, or that is more than the maximum lease ttl (1 hour; a longer ttl is capped to it) plus 60 seconds in the future (a clock stepped back), counts as expired. A zombie holder is dead. The state directory must be used from one pid namespace (a holder in another namespace may read as dead, which is safe because commit is a compare-and-set). Commit does not check the lease: a taken-over holder may still commit, and the compare-and-set decides. There is no per-query lease: a query listing writes only through one transaction.
- Every digest write is a compare-and-set: `UPDATE prs SET ... , rev = rev + 1 WHERE pr_id = ? AND rev = ?` inside `BEGIN IMMEDIATE`, with the check that at least one `sources` row for the PR still exists. If either fails the transaction is rolled back, its events are discarded, `prs.skipped_conflict` is counted and nothing is committed. A poll and a `watch add` baseline may therefore both snapshot the same new PR; the second write is discarded. `watch add` and `watch remove` take no lease. `watch remove` of the last source drops the row; a commit in flight for it is discarded by the check. Inside the same transaction each event's `labels` and `watches` are read and then the sources removed by the membership rule are deleted (Watches, owners and members), so an event's `labels` and `watches` include a source the same commit removes; the transaction also verifies that the snapshot's `pr_id` equals `prs.pr_id`. A snapshot that shows `closed` is discarded (no commit, no counter; its persisted trigger retries it) when the row's `listed_updated_at` at commit is larger than the snapshot's `updated_at`, because a listing has already seen a newer state, so a concurrent poll cannot make a reopened PR terminal. The comparison uses the snapshot's own `updated_at` (the commit takes it as `snapshot_updated_at`, not the stored `snap_updated_at`, which is the larger of it and the time listed at the start); a closed snapshot whose time cannot be parsed (or has no zone) is discarded as a newer listing. When the membership rule removes the PR's last source in the commit, the events and the deletion are still committed and the row is dropped (no digest write).
- A PR whose lease is held by a live other poll counts as locked. **`already_running`** is defined here once: `already_running: true` is reported when at least one PR needed a snapshot and every such PR was held by a live other poll's lease; then `prs.skipped_locked` is the only non-zero counter and the report has the full shape.
- `poll.max_duration` (default 15m) stops new snapshots (Poll cycle, step 4).

### What is polled

The cheap trigger is `updated_at` through `prs`. It is reliable for new comments, reviews, pushes, labels, review requests and draft changes, and blind to check completion, thread resolution (GitHub) and, on GitLab, approvals, finished CI jobs and bot-note edits (spikes A and B). That is why an unsettled PR (State) is snapshotted on every cycle until it settles or becomes `ci_stuck` (Poll cycle, step 4 (c)), and why a periodic full pass exists. A storm of unsettled PRs is bounded by `poll.max_snapshots`. A change that only the full pass can see (a GitLab approval, for example) can therefore be reported up to `poll.full_every` cycles late; the report and `show` print `last_full_at`.

### Digest

The digest holds exactly what the diff compares: `head_sha`, `state` (`open`, `closed`, `merged`), `draft`, `mergeable` (shown in `show`, no event), `blocked_by` (sorted codes as forgectl prints them, a code is `{code}` or `{code: other, detail}`, `detail` kept truncated), `ci` (`state`, `head_sha` (forgectl's `ci.head_sha`), `hold` (the number of consecutive snapshots that reported the same new state, 0 when none), `hold_to` and the `checks` map of the **counted** checks only; uncounted checks are neither stored, diffed nor reported), `review_decision` and `approvals_at_head` (`null` is unknown, never zero), `reviewers` (keyed by the reviewer key: `id` when forgectl gives one, else `login:` plus the lowercased login (forgectl's `login` is never null in `latest_by_reviewer`); per key `state`, `commit_sha`, `at`, `can_push`), `seen: {comments, reviews}` (sets of ids, stored as sorted, de-duplicated lists of the ids that match `[A-Za-z0-9:_=-]{1,128}`; a set, never a watermark), `pushed_at`, `merged_head_sha`, `merge_commit_sha` and `baselined: {reviews, threads, ci}`. The diff reads the old digest, the new digest, the new snapshot (only for event payload fields: comment `author`, `path`, `line`, `side` and times, and a reviewer's `login` and `is_bot`, found by reviewer id among the snapshot's reviews, else the `login` of the `latest_by_reviewer` item for that key with `is_bot` `null`; see Events, common fields) and the row's `rebaseline` flag; it reports only snapshot ids that match the seen-id pattern above and are not in `seen`. Every other stored value is a column of its own (State). No body, title, URL, branch name or any text beyond the one-line fields.

Checks are keyed by the first 32 hex characters of sha256 of the full sanitized `name`, a NUL and `url` (hashed before truncation); the digest stores `{name (truncated), state}` per key, never the URL, at most 500 keys (an overflow count beyond).

Digest shape (the contract for the diff, hold and poll code; the digest is an internal storage shape with no JSON schema under `schemas/`, so "validated against schemas where applicable" does not apply to it). The keys are exactly `head_sha`, `state`, `draft`, `mergeable`, `blocked_by`, `ci`, `review_decision`, `approvals_at_head`, `reviewers`, `seen`, `pushed_at`, `merged_head_sha`, `merge_commit_sha` and `baselined`; `ci` has exactly `state`, `head_sha`, `hold`, `hold_to`, `checks` and `checks_more`; `seen` has exactly `comments` and `reviews`. Details:

- `ci.checks_more` is the number of counted checks over the 500 cap (0 when none). It is a digest field only; the `ci` event's `checks_more` (Events) is a different number.
- A check entry is `{name, state}` with `state` one of `passing`, `failing`, `pending`, `skipped` or `unknown` (a value forgectl sends that pr-watch does not know is stored as `unknown`). Checks that share a key (same name and same URL) merge into one entry, the worst state wins (`failing`, then `unknown`, then `pending`, then `passing`, then `skipped`), independent of order. When over 500 keys remain, the 500 smallest keys are kept.
- `reviewers` entries are `{state, commit_sha, at, can_push}`, never a login. The reviewer key is `id` when forgectl gives one, else `login:` plus the lowercased sanitized login; a login so long that the key would exceed 256 characters is replaced by `login:#` plus 32 hex characters of sha256 of the full lowercased login. An entry with neither a valid id nor a login is skipped. `state` is `approved`, `changes_requested`, `dismissed` or `unknown` (a state pr-watch does not know keeps the previous entry for that key when there is one, else is `unknown`). When forgectl lists one reviewer key more than once, the entry with the latest `at` instant wins (timestamps are compared as UTC instants, any offset; an unparseable `at` ranks lowest), then the larger `commit_sha`, then the state (`changes_requested`, `approved`, `dismissed`, other), then `can_push` (`true`, `false`, `null`), then the entry's canonical JSON, so the result never depends on input order.
- Bounds: `blocked_by` keeps the 100 smallest entries by (code, detail); more than 1000 distinct reviewer keys make the `reviews` part incomplete (nothing is truncated); more than 10000 distinct ids in `seen.comments` or `seen.reviews` make the `threads` or `reviews` part incomplete. 10000 is twice what forgectl can list (50 pages per list), so a real snapshot never reaches it; it exists so that a corrupt snapshot cannot grow the digest.
- `ci.hold` is always 0 and `ci.hold_to` is always `null` in a digest built from a snapshot; the hold (CI hold, Events) is applied afterwards, taking the counter from the previous digest. `ci` is never `null`: a `ci` part that is incomplete and has no previous digest is `{state: null, head_sha: null, hold: 0, hold_to: null, checks: {}, checks_more: 0}`, and a stored previous `ci` or `reviewers` that is malformed (wrong types, non-finite numbers, oversized) is replaced by the empty shape, not copied.
- The `ci` event's `counts` and the unsettled rule are computed by the diff from the snapshot, not from the digest, because the checks merge and the cap make digest counts unreliable.
- `approvals_at_head` `null` is unknown. A value that is not a count, or is larger than 2**53, is `null` even when the previous digest had a value (the one exception to keeping the previous value). `draft` may be `null` (an unreadable value with no previous). `head_sha` may be `null` (unreadable with no previous); the diff then emits no `pushed`.
- `seen` is replaced by each snapshot in which its part is complete; it is not a union over snapshots. An id that disappears from a snapshot and reappears, or a reviewer key that flaps (an `id` present, then `null`), can therefore fire again; this is accepted. A reviewer whose state is `unknown` is no event as `to`; as `from` it counts as no entry, so a later `approved` or `changes_requested` fires.

Part map. PR object (always present): `head_sha`, `state`, `draft`, `mergeable`, `blocked_by`, `pushed_at`, `merged_head_sha`, `merge_commit_sha`. Part `reviews`: `seen.reviews`, `reviewers`, `review_decision`, `approvals_at_head`. Part `threads`: `seen.comments`. Part `ci`: `ci`. The part `review_requests` and `teams_visible` are not used. The schemas are pinned to a forgectl version in `tests/`.

Parts forgectl lists in `incomplete` (`reviews`, `threads`, `ci`; `review_requests` is not used and is ignored if forgectl lists it), and parts pr-watch cannot read, are neither compared nor overwritten. A part is also treated as incomplete when: for `ci`, `ci.complete` is `false`, `ci.state` or `ci.head_sha` is missing or not a value pr-watch knows, or `checks` is not a list; for `reviews`, `reviews` or `latest_by_reviewer` is not a list, or a bound above is exceeded; for `threads`, `threads` is not a list or the `seen` bound is exceeded. `incomplete_parts()` in the digest code is the authoritative set for the poll (the part list the commit uses for `incomplete` counters); a snapshot that is not an object is all-unknown, every part incomplete. Incomplete parts are neither compared nor overwritten: absence from an incomplete part means nothing, and no event of a part is emitted from a snapshot where that part is incomplete. A PR whose list exceeds forgectl's caps (more than about 5000 comments or reviews, or a GitLab fork pipeline) therefore never produces events of that part; this is permanent and visible. The row keeps `incomplete` as a map part to the number of consecutive snapshots in which it was incomplete. `list` and `show` print `incomplete` (array of part names) and `incomplete_snapshots` (max count); the poll report has `prs.incomplete` (database-wide current count of PRs with a part incomplete at least `failures.unreachable_after` snapshots in a row) and `post-poll` has `degraded` (the same count). `log.jsonl` gets a `part_incomplete` record (`pr_id`, `pr`, `part`, `snapshots`) written once when the count reaches `failures.unreachable_after`. It fires only on exact equality and is suppressed for a merged or closed result, so a part that crosses the threshold while the PR is closed is not reported after a later reopen (known, accepted).

A digest is bounded: `seen` holds at most 10000 ids per list (above that the part is incomplete, see Digest shape), checks at most 500 keys, `blocked_by` at most 100 entries and `reviewers` at most 1000 keys.

`baselined` of a part that is incomplete in the building snapshot keeps the previous flag, so an unbaselined part stays unbaselined. The digest builder takes a `rebaseline` argument (the row's flag): when set, every part that ends up incomplete is marked unbaselined (its old data is kept), so a part that completes later is baselined silently instead of being diffed against stale data. The commit (State, transaction 2) is what clears `rebaseline` and sets `baselined_at`.

### State

Everything pr-watch persists is in `state.db` (Files). Every persisted value lives in exactly one column of the tables below, each with its writer (Transactions). Tables:

- `meta`: `store_id`, `schema_version`, `pruned_through_seq` (highest seq ever deleted, 0 at creation), `last_prune_at`, `last_poll_finished_at`, `hosts_cache` (JSON list of `{host, backend, in_scope}` and `fetched_at`).
- `hosts`: `host`, `backend`, `poll_count_since_full`, `full_pass_started_at`, `last_full_at`, `last_enumerated_at`, `paused_until`, `pause_step`, `low_water_until`.
- `scopes`: `repo`, `watermark` (host time; created by a repo's first listing, deleted when no per-PR row refers to the repo).
- `watches`: `id`, `kind` (`pr` or `query`), `key` (the Watch key), `created_at`; `owners` (watch, owner); `labels` (watch, owner, label); `sources`: `pr_id`, `watch_id`, `left_count` (0 to 2; query sources only, Watches, owners and members); `leases`: `pr_id`, holder pid, start time, boot id, `expires_at`.
- `events`: `seq` (INTEGER PRIMARY KEY AUTOINCREMENT), `id`, `type`, `pr_id`, `pr`, payload JSON, `detected_at`, labels JSON. The store enforces a backstop on what it appends, above the 256-character host-field cap: payload at most 128 KiB encoded, strings at most 4096 characters (valid UTF-8), nesting depth at most 6, integers within +/-2**53, labels at most 256 and unique, `pr` at most 512 characters, and the common fields of `schemas/event.json` (`repo`, `occurred_at`, `head_sha`, `watches`) present and well-formed.
- `prs`: `pr_id`, `pr`, `repo`, `host`, `status` (`active`, `terminal`, `unreachable`), `terminal_at`, `terminal_kind` (`merged`, `closed`), `rev` (integer, +1 on every digest write), `digest` (JSON, or null before the baseline), `snap_updated_at` (host `updated_at` of the last committed snapshot), `listed_updated_at` (largest host `updated_at` an enumeration reported for the PR), `last_polled_at` (last committed snapshot), `last_attempt_at`, `failure_count`, `last_failure_code`, `incomplete` (JSON map part to consecutive-snapshot count), `unsettled_since`, `rebaseline` (boolean; set by reactivation, cleared by the next snapshot commit), `baselined_at`.

Foreign keys: `owners`, `labels` and `sources` rows are deleted with their watch, `sources` with their PR (`ON DELETE CASCADE`), and a PR row is deleted in the same transaction as its last source, so no orphan can exist. The drop is a trigger on `sources` deletes, so it also removes the PR's digest at once: a caller that moves a PR between watches must insert the new source before deleting the old one, or the `prs` row (and its digest) is lost.

Definitions. A **source** is a row of `sources`: a per-PR watch, or a query watch that includes the PR. A PR is **unsettled** when `ci.state` is `pending`, `ci.hold` is above 0, or `blocked_by` holds `mergeability_unknown`. `unsettled_since` (local time) is set by the snapshot commit when the PR becomes unsettled and it is null, is reset to the commit time whenever `head_sha` changes, and is cleared when the PR is settled. **`ci_stuck`** is true when the PR is unsettled and `now - unsettled_since` is at least `ci.pending_max_age` (default 6h); a stuck PR is snapshotted only on full passes. `list` and `show` print `ci_stuck`. `baselined_at` is the commit time of the last snapshot that baselined any part silently (first sight, a reopen, a late part baseline); it is null before the first snapshot. **changed**, in `watch add` results, is true when any stored fact changed.

Transactions. (1) Enumeration of one scope: `listed_updated_at`, new member rows and sources (after verifying the watch exists), `left_count`, reactivations (with `rebaseline`), `hosts.last_enumerated_at`, the repo watermark and the incomplete-listing marks (Poll cycle, step 2), and deletion of `scopes` rows no row refers to. (2) Snapshot commit: events (with labels and watches read here), digest, `rev` + 1, `snap_updated_at`, `last_polled_at`, `failure_count = 0`, `incomplete`, `status`, `unsettled_since`, `baselined_at` (set when this commit baselined any part silently, including a reopen), `rebaseline = 0`, and the removal of sources (Watches, owners and members). (3) Failure: `failure_count`, `last_failure_code`, `last_attempt_at`, `status` (the status of a `terminal` row is never changed by a failure). (4) Host state (`paused_until`, `pause_step`, `low_water_until`, `poll_count_since_full`, `full_pass_started_at`, `last_full_at`) is written after the host's cycle. (5) `meta.last_poll_finished_at` is written by the poll's last step, after the hooks drained and `post-poll` ran and before the report is printed, only when the poll was not restricted (`--pr`, `--repo`), was not `already_running`, ended with exit 0, was not interrupted and observed something (at least one listing or snapshot succeeded, or the store has no watches); `truncated` polls count. A poll that observed nothing (every host paused, every call failing per PR or per scope) leaves it unchanged, so a stale value is the blindness signal. It is the one freshness field (a poll that failed a whole host does not move it); a fresh value still does not mean every host or PR was observed (Consumer notes). (6) Hooks write only `log.jsonl`.

### Events

An event is one detected difference. The types and the exact rule for each:

| Type | Fires when | Extra fields |
|---|---|---|
| `opened` | A query-watch member is seen for the first time (its first snapshot) and its `created_at` is at or after the creation time of the oldest query watch that holds it: the PR was opened while it was being watched. Never for a PR a per-PR watch names, never on reactivation, never for a PR that existed before the watch, never for a PR with a retained event. See Opened and reopened below. | none |
| `reopened` | A stored `closed` PR is shown `open` again, by a reactivation or by a snapshot of a row not yet reactivated. Never from `merged`. See Opened and reopened below. | none |
| `pushed` | `head_sha` differs from the stored one. Never keyed on `pushed_at` (a normal push reports a committer date up to minutes early). | `from_sha`, `to_sha`, `forced` |
| `comment` | A general comment id (`gh:ic:`, or on GitLab a non-system note `gl:n:` of a discussion without a position) is not in `seen.comments`. Edits, minimizing and deletions are not events. | `comment_id`, `thread_id`, `author` |
| `review_comment` | An inline comment id (`gh:rc:`, or a non-system note of a positioned GitLab discussion) is not in `seen.comments`. | `comment_id`, `thread_id`, `author`, `path`, `line`, `side`, `commit_sha` |
| `review` | A review id (`gh:r:`) is not in `seen.reviews`. GitHub only; GitLab has no review objects and never emits it. | `review_id`, `author`, `review_state` |
| `approved` | A reviewer's `latest_by_reviewer` entry has state `approved` and the stored entry for that reviewer key was not `approved`, or its `at` differs, or (both `at` null) its `commit_sha` differs (`at` values are compared as UTC instants, any offset or fraction form; raw text only when neither parses; a stored `unknown` state counts as no entry). One event per reviewer per snapshot. A new approval after a push (same state, new `at` or `commit_sha`) fires again. The event is not proof that the head is approved: on GitLab `commit_sha` and `approvals_at_head` may be null (unknown), and `can_push` says whether the approval counts; consumers that merge on it read forgectl. | `reviewer`, `commit_sha`, `at`, `can_push`, `approvals_at_head` |
| `changes_requested` | Same key as `approved` with state `changes_requested`. A dismissal (state `dismissed`) is not an event. | `reviewer`, `commit_sha`, `at`, `can_push` |
| `ci` | `ci.state` changes between `pending`, `passing`, `failing` and `none` (a change involving `none` after the hold below). One event per change. | `from`, `to`, `checks`, `checks_more`, `counts`, `for_head` |
| `ready` | `draft` goes from true to false. It does not mean mergeable; consumers read `ci` and `blocked_by`. `from_blocked_by` and `blocked_by` are the codes in the stored digest before the snapshot and after it, each a sorted array in the Digest form. | `from_blocked_by`, `blocked_by` |
| `merged` | `state` becomes `merged`. | `merged_head_sha`, `merge_commit_sha` |
| `closed` | `state` becomes `closed` (not merged). | none |

Common fields on every event: `id`, `seq`, `type`, `pr`, `pr_id`, `repo`, `detected_at`, `occurred_at` (below, else `null`), `labels` (the union set), `head_sha` (the digest's head after the snapshot, the head at detection, not the head a comment was made on), `watches` (the ids of the watches that include the PR). `detected_at` is the time of the commit transaction; `labels` and `watches` are read inside that transaction (a removed watch is not listed, a just-added one is); `thread_id` is forgectl's thread id for the comment, `null` where forgectl gives none (a `gh:ic:` general comment). `author` and `reviewer` are `{id, login, is_bot}`: `id` from forgectl (nullable, opaque; consumers compare ids, not logins), `login` may be `null`, `is_bot` may be `null`. For a `reviewer` the `id` is the reviewer key, `null` for a `login:` key; `login` and `is_bot` come from the latest review (by `submitted_at`, an unparseable one lowest) in the snapshot whose author id is the key; with no such review `login` is the original-case sanitized `login` of the `latest_by_reviewer` item for that key (the one the digest keeps when there are several) and `is_bot` is `null`; a hashed overlong `login:#` key has `login` `null`; a consumer must treat `is_bot: null` as not a human. `review_comment` also carries `commit_sha` (the thread's anchor commit, nullable). Every sha in an event, payload and hook (`head_sha`, `from_sha`, `to_sha`, `merged_head_sha`, `merge_commit_sha`, `commit_sha`) is 40 lowercase hex (sha-1) or 64 lowercase hex (sha-256); `schemas/defs.json` `sha` is `^(?:[0-9a-f]{40}|[0-9a-f]{64})$` (additive: every previously valid value stays valid), and the digest and the store accept exactly the same set, so a 41 to 63 character value is unreadable (`null` in the digest) and never in an event. The sha-256 widening is for the events: `forgectl compare` is still called only with 40-hex shas (above), so for a 64-hex push `forced` is `null`. The common `head_sha` is the new digest's head when valid, else the stored digest's head (a null or unreadable new head does not suppress other events); with no valid head an event other than `pushed` is dropped. The event objects are the closed shape of this version; consumers must ignore unknown fields and types and must not validate strictly.

`occurred_at`:

| Type | `occurred_at` |
|---|---|
| `comment`, `review_comment` | the comment's `created_at` |
| `review` | `submitted_at` |
| `approved`, `changes_requested` | the entry's `at` |
| `opened` | the snapshot's `created_at` |
| `reopened` | `null` (a snapshot carries no reopen time) |
| `pushed` | the snapshot's `head.pushed_at` (a committer date, may be early) |
| `merged` | `merged_at` |
| `closed` | `closed_at` |
| `ci`, `ready` | `null` |

`checks` lists in the `ci` event the checks whose key appears, disappears or changes state between the stored and the new digest, ordered by name then key, at most 20 (`checks_more` for the rest), each `{name, from, to}` with null `from` or `to` for a check that appears or disappears; the array may be empty. The event also carries `counts: {passing, failing, pending}`; `counts` and `checks` range over the counted checks (Digest); `for_head` is the new `ci.head_sha` (forgectl's, which may differ from `head_sha` for a GitLab merged-results pipeline). `passing` means no counted registered check is failing or pending and one passed; it does not say every expected check registered, and a consumer that gates an action pins the head and re-reads `ci` through forgectl. `forced` is computed from `compare <pr> --from <stored head> --to <new head>` only when `detect_force_push` is true: `diverged`, `behind` or `unavailable` is `true`; `ahead` is `false`; `identical`, exit 20 (`too_large`) or a failed call is `null` (with `--no-diff` a `too_large` can arise only from a timeout or the read cap, and is `null` too); pr-watch passes `--no-diff` (only `status` is read), so the call carries no diff, and its output is still bounded by `forgectl.max_output_mib`. `detect_force_push` defaults to false; consumers that need `forced` set it per repo.

Rules that apply to all types:

- **Dropped events.** An event that would fail `schemas/event.json` or the store's validation (no valid head as above, a malformed `repo`, `pr` or `pr_id`, a comment or review id outside forgectl's id forms, a review state outside the schema's enum, a `ci` event whose `for_head` is not a valid sha (unreachable from a real snapshot)) is never stored and never silent: the diff returns the drops beside the events as `dropped`, a list of `{type, reason}` with `reason` one of the fixed codes `invalid_head_sha` (also for a `ci` event with no valid `for_head`), `invalid_identity`, `invalid_comment_id`, `invalid_review_id`, `invalid_review_state`, and the poll logs the `dropped` reason codes (no host text). A value that is merely unusable (an out-of-range line, a bad side, a null sha field) becomes `null` in the event and is not a drop; a minimized comment is not a drop.
- **Unknown stored state.** A stored `state` that was never readable (`null`) is treated like first sight for `merged` and `closed` (as if the PR had been `open`), so a later `merged` or `closed` is not lost; other events compare as usual. `review_comment.line` is `null` unless an integer from 0 to 2**53; `review` is emitted for GitHub-backed PRs only.
- **Baseline.** The first snapshot of a PR (a per-PR `watch add`, or the first snapshot of a query member) fills the digest and emits nothing, with two exceptions: a PR already `merged` or `closed` at that moment emits that one event once, and then expires normally; a query member that qualifies for `opened` (below) emits that one event first. Baselines are per part: the digest keeps `baselined: {reviews, threads, ci}`; a part that is complete in a snapshot and not yet baselined is filled silently and flagged; a part listed in `incomplete` stays unbaselined and is baselined silently by the first snapshot where it is complete. A snapshot of a row with `rebaseline` set follows the same silent rule, with the exceptions of `pushed`, `merged` and `closed`. Comments and reviews that exist at the baseline are never events (consumers read current state through forgectl on first sight).
- **Opened and reopened (1.x).** forgectl v0.55.3 `prs` items carry the host's `created_at`, as does the snapshot's PR object; pr-watch reads the snapshot's, so `opened` costs no extra call. `opened` fires at most once per PR, at the PR's first snapshot, when all hold: the events table holds no event for the PR (any type; keyed by `pr_id`, which survives a row deletion, via the existing `events_by_pr` index, so no store change or migration is needed), the row is held by a query watch, no per-PR watch names the PR (the caller named it, so it is not news), and the snapshot's `created_at` (a timestamp with a zone, else no event) is at or after the `created_at` of the oldest query watch holding the row. The watch's own first enumeration therefore never emits it (every PR it lists existed before the watch), and neither does an old PR that joins later (a filter change, a PR that now matches); the first snapshot of such a PR is the silent baseline. A PR created between `watch add` and the first enumeration counts as opened while watched. It fires before the terminal event of the same snapshot (a PR already `merged` or `closed` at first sight emits `opened` then that event). A PR that already has a retained event (its own `opened` included) never gets a second `opened`: a member that leaves and rejoins the listings until its row is dropped (search lag, a filter flip such as draft or label, two missed complete listings), and a closed PR whose row expired and that is reopened later, return as a new row with a silent baseline. Residual risks: (1) a second `opened` is possible only after every earlier event of the PR was pruned (`retention.events`, at least 30 days), and consumers still dedupe `opened` by PR. (2) A host that reports `created_at` in whole seconds can lose a PR created in the same second as `watch add` (the comparison is `created_at` >= the watch time, with microseconds). (3) Clock skew: a host clock behind the local clock by d loses `opened` for PRs created within d after `watch add`; a host clock ahead gives a spurious `opened` for a PR created up to the skew before it. (4) The over-cap fallback (snapshot `too_large`, then `show`) emits only `merged` or `closed`, never `opened`. (5) If a newer query watch enumerates a PR before the older holding watch has, the newer watch's time is used and `opened` can be missed. `reopened` fires when the stored digest says `closed` and the snapshot says `open`, with or without the row's `rebaseline` flag (a reactivated row or one that missed the flag); it is in addition to the silent re-baseline and to `pushed` (so a reopen with a moved head emits `reopened`, then `pushed`), and carries no extra fields (`occurred_at` is `null`). A row whose stored digest is `merged` is final and emits nothing; a PR that goes `closed` to `merged` emits only `merged`.
- **Several changes in one snapshot** produce several events, in this fixed order: `opened`, `reopened`, `pushed`, `review`, `comment`, `review_comment`, `approved`, `changes_requested`, `ci`, `ready`, then `merged` or `closed`; inside a type by ascending `(created_at, id)` of the source item (`approved` and `changes_requested`: by reviewer key, then `at`; `ci` and `ready` are single). No order holds across PRs except by `seq`.
- **Comment unit.** The event unit is a comment id: `gh:ic:` fires `comment`; `gh:rc:` fires `review_comment`; on GitLab each non-system note (`gl:n:`) of a discussion fires `comment` when its discussion has no position and `review_comment` when it has one, so a reply in an old discussion fires. `thread_id` is the thread's id. `seen.comments` holds every comment id found in `threads` (all kinds); `seen.reviews` holds `gh:r:` ids. A comment first seen with `minimized: true` is added to `seen` without an event; later minimizing of a seen comment is not an event.
- **CI hold.** A change of `ci.state` in which either the stored or the new state is `none` is held: the digest keeps the previous `ci` (`state`, `head_sha` and `checks`) and sets `ci.hold` to the number of consecutive snapshots that reported the same new state (1 for the first) and `ci.hold_to` to that state; the change is committed, and its `ci` event fires, at the snapshot where `ci.hold` would exceed `ci.settle_polls` (default 1: the second consecutive snapshot; 0 means no hold). A snapshot that reports the stored state, or another state, resets `hold` to 0 (and starts a new hold if that other state involves `none`). A change between `pending`, `passing` and `failing` is never held. While `ci.hold` is above 0 the PR is unsettled (snapshotted every cycle) and `list` and `show` print `ci_state: null` and `ci_stale: true`. Otherwise `ci_state` is the digest's `ci.state`, `ci_stale` is false and `ci_head_sha` is the digest's `ci.head_sha` (forgectl's, which may differ from `head_sha` for a GitLab merged-results pipeline; that is information, not staleness). `passing` is never inferred from `none`. No `ci` event is emitted from a snapshot whose `ci` part is incomplete (the stored state is frozen).
- **Hold, ready and `ci` payload details.** A held `ci` keeps the stored `state`, `head_sha`, `checks` and `checks_more` and overwrites only `hold` and `hold_to`; a carried `hold` that is negative or not an integer counts as 0. An incomplete `ci` part freezes the state and the hold. A silent `ci` (not baselined, or under `rebaseline`) adopts the new `ci` as stored, with the hold cleared. `ready` is silent under `rebaseline` only (it has no part) and fires only for a stored `draft` that is exactly `true` and a new one exactly `false`; `from_blocked_by` and `blocked_by` keep only items of the schema shape (`code` matching `^[a-z_]{1,64}$`, a one-line `detail` of at most 256 characters only for `other`). The `ci` event's `from` and `to` are the stored and new `ci.state`; `checks` lists the check changes (a check appearing, disappearing or changing state, by name then key, at most 20) and `checks_more` counts the rest and is present only when above 0. `ci.settle_polls` that is not an integer (or is a boolean) counts as 1, a negative one as 0. The digest the diff returns (`ci` with the hold applied) is the one the poller stores.
- **GitLab.** `review` never fires. `approved` and `changes_requested` come from `latest_by_reviewer` on both hosts. `approvals_at_head` is `null` where the project does not reset approvals on push, which means unknown. A GitLab `outdated` value is not used. On GitLab `changes_requested` has `at` and `commit_sha` null, so its key never changes while the state stays; it fires only on a state transition, and a second request for changes after a push is not an event.
- **Terminal.** After `merged`, a PR is final. After `closed`, a reopen is a silent re-baseline except for `reopened` and `pushed` (PR status). A reopen is detected from the row's `rebaseline` flag or from a stored `closed` that the snapshot shows `open`. A row reactivated by a listing that the snapshot shows `closed` again emits `closed` once (the earlier closing was already reported; the reopen was never seen); the flag is cleared by that commit, so the next snapshot is silent. Known residual risk: a stale listing can reactivate a PR that is still closed, so a closed PR may emit `closed` a second time (the flagged closed-again rule above); that commit also refreshes `baselined_at`.
- **No per-snapshot event cap.** forgectl bounds every list to 50 pages (about 5000 items), so the events a PR can produce from ids are bounded; the cost of a flood is hook starvation, handled by the per-PR sub-cap (Hooks), and `events --limit` paging.

### Pacing and backoff

- **Host pause.** A `rate_limited` failure with `retry_after` pauses that host until then, but never for more than 1 hour (a larger `retry_after` is clamped; the host is probed again after the clamp). A stored pause more than 1 hour ahead of now is invalid (a clock stepped back, a corrupt value): it counts as expired, the host is probed again and the next write clears it. The write itself keeps a stored pause up to 2 hours ahead of the poll's end time, because a concurrent poll that finished later may have written one up to 1 hour past this poll's time (the later of two pauses wins); a pause beyond that is overwritten or cleared. Without `retry_after` the pause is 1 minute and doubles on each further `rate_limited` result up to 15 minutes (`pause_step` is persisted in `hosts`); a success resets it. A paused host is skipped (reported as `paused_until`), other hosts continue; the host's remaining queue and listings are cancelled for this cycle. A host's state (pause, low water, pass counters) is written when that host's cycle ends, not once at the end of the poll: a host that runs no snapshot (rate limited or failed while listing, paused, nothing chosen) is written right after enumeration, a host with snapshots as soon as its queue has ended, so a poll killed later, or an overlapping one, never loses a pause.
- **Low water.** At cycle start a host is limited iff `now < hosts.low_water_until`. A limited host is still listed and snapshots only groups (a) to (d) of the Poll cycle; groups (e) and (f) wait (a full pass in progress stays in progress). After the host's cycle, if the lowest numeric `rate_limit.remaining` of that host's calls is below `poll.host_low_water` (default 100), `low_water_until` is set to that reading's `reset_at`, else it is cleared. `--full` overrides low water, not a host pause. A host that reports `null` (a self-hosted GitLab without limit headers) is never limited. The low water changes only when the host gave a result (a successful listing, or a snapshot that committed or was discarded on a conflict); a failed call, a rate-limited one included, changes neither the low water nor `pause_step`. A stored `low_water_until` more than 1 hour ahead is read as 1 hour from now, and the next result rewrites it.
- **Full pass.** `poll_count_since_full` increases by one for every unrestricted cycle (no `--pr`, no `--repo`) in which the host was listed and was not paused. When it reaches the host's `full_every`, or `--full` is given, and no pass is in progress, the cycle sets `full_pass_started_at` to now and resets the counter. A pass is in progress while `full_pass_started_at` is set; it ends (and `last_full_at` is set to now, `full_pass_started_at` cleared) in the first cycle after which every `active` or `unreachable` row of the host is done for the pass: its `last_polled_at` or `last_attempt_at` (a failed attempt counts) is not before `full_pass_started_at`, so a PR that fails every time is tried once per pass and cannot keep a pass open. `poll_count_since_full` is not reset when a pass ends, so it counts the cycles since the last pass started: a pass that lasts `full_every` cycles or more is followed at once by the next. `--pr` and `--repo` polls never count and never start or end a pass; a `--pr` poll still plans the host of its target (a host whose only row is terminal-closed included) and persists a pause or low-water reading.
- **Pool.** `poll.concurrency` workers per host: `hosts.<h>.concurrency`, else `poll.concurrency` if set, else 4 on GitHub and 2 on GitLab (backend from `whoami`, else from the `backend` of the host's first committed snapshot, which is stored in `hosts.backend`: a host with only per-PR watches is never asked by `whoami`, so its first cycle uses the GitLab defaults when it is not `github.com`). The same holds for `full_every` (6 on GitHub, 12 on GitLab).
- **Cost accounting.** `requests_estimate` is `snapshots x 7` (GitHub) or `snapshots x 21` (GitLab) only (no page count; `compare` and `show` calls are not counted), an estimate. A GitHub snapshot is 5 to 8 requests (5 when forgectl's `hosts.<host>.me` is set); a GitLab snapshot was 19 to 22 requests and 11 to 14 seconds in the design spikes.

### Failures

forgectl results are classified by exit code and error `code`. One table says what each outcome means for three kinds of call: a PR call (`snapshot` or `show` of one PR), a repo listing (`prs --repo`) and a host call (`prs --host`, `whoami`). Every code not listed is the `internal` row.

| Outcome | A PR call | A repo listing | A host call |
|---|---|---|---|
| success (exit 0 object) | commit; `incomplete` parts as in Digest | State transaction 1 | State transaction 1 |
| `rate_limited` (exit 12, with or without `retry_after`) | host pause (Pacing and backoff), no counter, no status change; the host's remaining queue and listings are cancelled for this cycle and PRs keep their persisted triggers; exit 0 | the same | the same |
| `auth_required`, forgectl `tool_missing` (`details.install`) | whole host this cycle: the host is in `failed` (kind `host`), the host's remaining queue and listings are cancelled, no counter, PRs retried next cycle; exit 12 | the same | the same |
| `host_rejected`, `unsupported_host_version`, `wrong_host_response` | `host_rejected` and `unsupported_host_version`: that PR's failure: counter +1, `last_failure_code`, a `snapshot_failed` record, a prominent report entry and a `post-poll` mention; the host continues. `wrong_host_response`: whole host this cycle, as `auth_required`, plus a `log.jsonl` error "the token may have reached another host and should be rotated" | whole host, as `auth_required` (`wrong_host_response` also logs the error); exit 12 | the same |
| `network_error`, `upstream_error`, unparseable stdout, a missing required field, a snapshot that is not a JSON object (`MalformedSnapshot`), a field of the wrong JSON type, nesting deeper than 32 levels or a lone surrogate in a key or string (local `contract`), `internal`, any unknown code, a negative return code, an exit above 128 (for example 137) or the call deadline (local `killed`), the output cap (local `too_large`) | retryable per PR: counter +1, digest kept, tried next cycle (`too_large` also takes the fallback below) | the repo scope failed this cycle (`failed` kind `repo`, watermark and triggers untouched, no counter, its PRs are still reached by their triggers and by full passes); exit 0 | the host listing or `whoami` failed this cycle (`failed` kind `query` for the open listing, `host` for `whoami`; no counter; the Host list rule for `whoami`); exit 12 |
| `not_found` (exit 10), `permission_denied` (exit 12) | permanent for the PR: counter +1 (`not_found` means unknown, never closed) | as the previous row (scope failed, no counter; the PRs then fall to the full pass where the PR column applies) | `permission_denied` fails the host listing as in the previous row; `not_found` is `internal` |
| `unknown_host` (exit 20) | permanent: counter +1 | scope failed, no counter | host failed (kind `query`, kind `host` for `whoami`); exit 12 |
| `pr_id_changed` (local: the snapshot's `pr_id`, or the `pr_id` of the over-cap fallback's `show`, differs from the stored row's, because a renamed or recreated repo name now names another PR) | no commit, `pr` is not refreshed, counter +1, a `snapshot_failed` record | not applicable | not applicable |
| exit 128+N while pr-watch was not signaled | interrupted: no counter, retried next cycle, the poll continues | scope or host not listed this cycle, no counter, exit 0 | the same |
| exit 2 (`usage`, `config_invalid`, `invalid_pr`) | a stored reference was rejected, which is a bug: counted as the `internal` row plus a `contract` warning | the same | forgectl's own `config_invalid` stops the poll with exit 12 `host_failed` |
| `--version` cannot run (missing, not executable, killed, over the deadline, output over the cap; see the Version rule for a wrong or non-zero answer) | tool: exit 12 `tool_missing` before any work | not applicable | not applicable |
| version below the minimum | tool: exit 12 `tool_too_old` | not applicable | not applicable |

The reported code (`failed[]`, `last_failure_code`) is forgectl's own code, except that `not_found` on a host call is reported as `internal`.

- **Counters.** Only the PR column rows that say counter +1 change `failure_count` (and `status` after `failures.unreachable_after`); a success clears it; `rate_limited`, `auth_required` and every listing failure never change a PR. A whole-host failure cancels the rest of that host's queue so the failing call is not repeated per queued PR. **Exit 12 from `poll`** is exactly: a row above marked exit 12, or forgectl missing or too old; pause, low water, `truncated`, per-PR and repo failures and `incomplete_listing` are exit 0. `failed[].ref` is the canonical `pr` for kind `pr`, the repo id for `repo`, the host for `query` and `host`.
- **Call deadline.** Every forgectl call has a wall-clock deadline of `forgectl.timeout` plus 10 seconds; the read loop stops at the output cap and at the deadline, and the child's process group gets SIGTERM, then SIGKILL after 2 seconds (or as soon as the leader has exited, so descendants that ignore SIGTERM die too), only while its leader is unreaped (local code `killed`). A leader that exits before the deadline ends the call normally even if a descendant still holds the pipes: what is readable is taken and the call returns; `timed_out` is set only when the leader was still running at the deadline. During a signal's shutdown (Signals) a child that ignores the SIGTERM is group-SIGKILLed 5 seconds after the shutdown began instead (longer than the 2 second grace, because forgectl's own cleanup of its children takes up to about 3 seconds), again only while its leader is unreaped. `compare` has the same deadline; a `compare` that exits 20 `too_large` or fails gives `forced: null`.
- **Over the output cap.** The snapshot is body-free (`--no-bodies`), so comment and review bodies no longer count toward the cap; what can still exceed it is the PR's own body or title, or an extreme number of comments, reviews or checks. When a snapshot fails `too_large`, pr-watch calls `forgectl show <pr> --json` (the PR object only, no threads) for terminal-state detection only. It first compares `show.pr_id` with `prs.pr_id`: on a mismatch nothing is stored and the failure is the `pr_id_changed` row (counter +1). If its `state` is `merged` or `closed`, the PR's one `merged` or `closed` event is stored with `merged_head_sha` and `merge_commit_sha` from it, the row goes terminal, and only `state`, `merged_head_sha` and `merge_commit_sha` are written to the digest (a row without a digest gets the same minimal digest with `baselined` all false; the digest's `baselined` flags are also written, all false on a `rebaseline` row, deliberately); nothing else is read, and no `pushed`, `ready`, `ci` or other event comes from this path. When the fallback stored a terminal state the counter is set to 0. A `show` that reports an open PR counts the `too_large` failure (counter +1), so a still-open over-cap PR becomes `unreachable` and is retried on full passes, each costing one `show` extra. A `show` that itself fails is classified by its own row of the table (it may pause the host and not count; no second `show` is made). The `pr_id` check and the open case come before `updated_at` is read, so another PR is `pr_id_changed` and an open one `too_large` even with an unreadable `updated_at`; a terminal `show` with an unreadable `updated_at` is a `contract` failure (the commit needs `snapshot_updated_at`). The event's `head_sha` is the stored digest's head when it is a valid sha, else the head `show` reports; with no valid head the event is dropped with `events_dropped` (`invalid_head_sha`) and the row still goes terminal. The job counts two calls in `calls`.
- **Version rule.** `MIN_FORGECTL` is a constant of the pr-watch release (`(0, 55)` in the 0.x line and still in 1.x: `snapshot --no-bodies` is present since forgectl 0.45), not a config key. Parse `^forgectl ([0-9]+)\.([0-9]+)\.([0-9]+)$` (ASCII digits, at most 9 each) once per process (poll and per-PR `watch add`) from `forgectl --version`; the found major must equal the constant's and the found minor must be at least the constant's, for 0.x as for later majors (patch is ignored). forgectl takes a new minor with every feature release, so an exact-minor rule would make every release refuse until pr-watch re-pinned; a breaking 0.x minor of forgectl is caught by the `contract` failure (every forgectl result is checked against the documented shape). Anything else, an unparseable string, a major other than the constant's or a non-zero exit is `tool_too_old` (`details.found` is the string or `unknown`); a `--version` call that cannot run at all (missing, not executable, killed, including an exit above 128, over the deadline, output over the cap) is `tool_missing`. The check is enforced: the client runs it before every other forgectl call (the result is cached once it succeeded), so no call reaches an unchecked forgectl.
- **Resolution.** The `forgectl` executable is resolved once per process against absolute `PATH` entries only; the resolved path and the version are logged. The gateway itself makes `argv[0]` absolute against the caller's working directory before the child's `chdir`, so a relative or empty `PATH` entry never resolves against the child's `cwd`.
- **Host list.** `whoami` is called per `hosts_ttl` (the host-call column of the table); exit 12 with an object is used (hosts in `errors` are failed this cycle); on a failed call the stale cache is reused with a warning (and one `host_failed` warn record per cached host, at most 20), and with no cache the query watches are skipped this cycle and listed in `failed`. A `whoami` failure with a usable stale cache does not by itself make the exit code 12 (the poll goes on with the stale host list and prints one warning line on stderr; the exception is forgectl's own `config_invalid`, which ends the poll with exit 12 and is listed in `failed` as kind `host` with `ref` `whoami`); a `whoami` failure with no cache (the query watches skipped) is a host-call failure and exits 12, listed in `failed` as kind `host` with `ref` `whoami` (a rate limit stays exit 0). A rate limit of the whole `whoami` call (`retry_after` or not) pauses every host of the host list in use (the stale cache), the stored host rows and the hosts that have PR rows, each clamped and persisted at once like any pause (a `--repo` poll pauses only its repo's host), and no host is listed that cycle, whether it is in the cache or not (a per-PR scope included); the next process honours the pause.
- **`unreachable`.** A PR becomes `unreachable` after `failures.unreachable_after` consecutive counted per-PR failures (default 5); it is snapshotted only on its host's full pass and clears on the first success. Whole-host failures never change PR status. PRs that became unreachable this cycle are named in `post-poll` (`unreachable: [{pr, pr_id, code}]`, at most 50), and `post-poll` fires when any occurred. A flap is not an event.

A failure never produces an event. `closed` and `merged` are never inferred from a failure or from a PR vanishing from a list.

### Signals

On SIGTERM, SIGINT or SIGHUP, pr-watch stops starting work, sends SIGTERM to the forgectl and hook process groups it started (only while their leaders are unreaped), releases its leases, writes `poll_end` with `interrupted: true` and exits 128 plus the number; nothing partial is committed for a PR in flight. A forgectl child exiting 128+N while pr-watch itself was not signaled is an interrupted PR: no counter change, tried next cycle, the poll continues. A command other than `poll` ends on the signal the same way (exit 128 plus the number, quietly; an open transaction rolls back). A signaled `poll` prints no report; each host whose queue had ended has already written its state, and a host whose listing was rate limited before the signal has its pause written. The signal wins wherever it lands: a forgectl call that ended because of it (killed by it, or refused after it) is neither a failure of a host or PR nor the exit 12 `tool_missing` envelope, and a signal during the end of the poll (host state, the hook drain, `last_poll_finished_at`) or before the report exits 128 plus the number with no report and no `last_poll_finished_at`. A signal after the report skips the daily prune and exits 128 plus the number; a prune cut by a signal stops between batches and does not stamp `last_prune_at`. A forgectl child that ignores the shutdown SIGTERM is group-SIGKILLed 5 seconds after the shutdown began (`SHUTDOWN_KILL_AFTER`), only while its leader is unreaped, so a signalled `poll` ends within about that plus the wait to reap the leader; a descendant that ignored the SIGTERM dies with the group even when the leader obeyed it. The first signal's number is the exit code for every command: later signals neither raise again nor change the code, and do not interrupt the unwind (a forgectl child's shutdown, a rollback). A signal that arrives while the poll's own snapshot commit is running lets that commit finish whole, then exits 128 plus the number; a signal before the stop check commits nothing, and one before the final `last_poll_finished_at` write is seen again inside that write's transaction, which rolls back. A signal that arrives before the CLI has started (during imports) also exits 128 plus the number, with no traceback.

## Commands

All commands take `--json`, `--config PATH`, `--verbose`, `--quiet` (Global flags). Every command that prints a PR prints it in `#N` form.

### `watch add`

`pr-watch watch add <pr> [--label k=v]... [--owner O] [--no-baseline]`
`pr-watch watch add --mine --open [--host H]... [--repo ID]... [--label k=v]... [--owner O]`

Adds the owner's reference to the watch (creating it), and unions the labels. The query form only records the watch (and validates its filters): it never baselines, and the first `poll` finds and baselines its members silently; `--mine` and `--open` must be given together (exit 2 `usage` otherwise), and filters are validated as in Identifiers and compared case-insensitively. The per-PR form first matches the reference against stored rows (canonical `pr`, URL form, case-insensitive), and the stored row decides whether a host is contacted. Baseline iff the row has no digest and `--no-baseline` is absent:

| Stored row before the call | Host contact | Result |
|---|---|---|
| none | one `forgectl snapshot <pr> --no-bodies --json` (it carries the canonical `pr` and `pr_id`); with `--no-baseline` one `forgectl show` instead, and the first `poll` baselines | `baselined: true` (false with `--no-baseline`); `events_emitted` is 1 if the PR was already `merged` or `closed`, else 0 |
| a row without a digest (an earlier `--no-baseline`, or a member not yet polled) | one `snapshot`, unless `--no-baseline` is given again | baselined now; `events_emitted` as in the previous row |
| a row with a digest (a member, another owner's watch, a concurrent poll) | none; only the source, owner and labels are added (compare-and-set discards a fetched snapshot) | `baselined: false`, `events_emitted: 0` |
| a row past `expiry.after_terminal` but not yet pruned | treated as absent: deleted and baselined as new in one transaction (PR status) | as the first row |

The write is a compare-and-set: if a row with a digest already exists (a member of a query watch, or another owner's watch, or a concurrent poll baselined it first), the fetched snapshot is discarded, only the source, owner and labels are added, and no events are emitted. `baselined: false` can also mean the baseline was deferred to the next poll: a row without a digest whose snapshot shows `closed` while a listing already saw a newer state is discarded (only the source, owner and labels are added). A snapshot fetched for a stored row refreshes its `pr` and `repo` (a rename) even when its baseline is discarded. An invalid reference exits 2 and a missing PR exits 10, recording nothing; a transient failure exits 12, recording nothing (so a retry is safe). A PR already `merged` or `closed` stores its one event now; `watch add` runs no hooks (a consumer reads the event through `events`), and a re-add after expiry stores the event again (consumers dedupe on `pr_id` and `merge_commit_sha`). The result always carries the PR (`pr`: the `pr_row` object, null for a query watch), so a consumer sees `state`, `status`, `terminal_at` and `terminal_kind` of an existing terminal row, for which no event is emitted. `cursor` is the events head read at the start of the same transaction as the write, so the event a merged or closed PR stores now (`events_emitted: 1`) is after it. It is for a consumer that has no stored cursor; a consumer that already holds a cursor ignores it (otherwise events between its last read and now are skipped); `created` and `changed` say whether anything was just made. Adding an existing owner and labels to an existing watch prints `changed: false` and does nothing else; a new owner on an existing watch adds the reference without a new baseline when the row has a digest. `--no-baseline` applies to the per-PR form only. `--host` and `--repo` apply to the query form only: on the per-PR form they are a usage error (exit 2, `details.kind: bad_combination`).

### `watch remove`

`pr-watch watch remove <pr> [--owner O]` and `pr-watch watch remove --mine --open [--host H]... [--repo ID]... [--owner O]`

Removes only the named owner's reference (and the labels that owner added). Idempotent: when the owner holds no reference (including a PR that is not stored or whose watch expired) it exits 0 with `changed: false` and `reason: not_held` or `pr_unknown`; `pr_unknown` also prints a warning line on stderr and the result includes the resolved reference (`reference`), so a typo or a stale name is visible (consumers remove by `pr_id`). An invalid reference is still exit 2. The watch ends when its last owner is gone; PR rows with no remaining source are dropped with their digests; stored events stay until retention. Expiry removes owners' references without an event. Removing never contacts a host. Expiry is applied by `prune` (PR status), not by `watch remove`: before `prune` runs, an expired but unpruned row is still stored, so `watch remove` acts on it like on any row (`changed: true`; the end state equals what `prune` would produce, so removal wins), and after `prune` has deleted it the result is `not_held` with `reason: pr_unknown`. `--quiet` silences the printed result only: the `pr_unknown` warning on stderr is printed regardless (Global flags). A command that finds nothing to remove (`not_held`, `pr_unknown`) takes no write lock. A query watch is addressed by its exact filters (the key); there is no partial match.

### `poll`

`pr-watch poll [--pr <ref>] [--repo <id>] [--full] [--no-hooks] [--hook NAME=CMD]...`

Runs one cycle (Poll cycle). `--repo <id>` limits snapshots and listings to that repo's per-PR scope plus the host listing's matching items (it advances only that repo's watermark; the host listing still writes `listed_updated_at` for all listed rows, but only items of that repo, matched case-insensitively, become members, reset `left_count` or are reactivated; it counts no absence and does not set `hosts.last_enumerated_at`; only the query watches that cover that repo's host are used; a restricted poll reports only its repo's host, so a `whoami` error or skip for any other host is neither a failure nor a `skipped` fact and never makes exit 12). `--pr <ref>` does no listing, forces that PR's snapshot, advances no watermark, and exits 10 when the PR is not stored (members count as stored); on a terminal-closed row it snapshots and reactivates it (silently, PR status) if the PR is open; on a merged row it exits 0 with `polled: false` (a merged PR is final); on an `unreachable` row it snapshots; under `already_running` the report prints `polled: false`. A restricted poll (`--pr` or `--repo`) never changes `poll_count_since_full` and never sets `last_poll_finished_at` (State). `--full` snapshots every active PR of the scopes it covers, ignoring the cheap trigger and `poll.max_snapshots`; `--no-hooks` stores events and skips hooks (for a catch-up run); `--hook <name>=<cmd>` (repeatable) adds a per-invocation hook to the configured ones (a static trusted string, never one built from event or host text): `NAME` must be one of the eleven hook names in the Hooks table (`on-<event>`, `post-poll`), else exit 2 `usage` with `details.kind: bad_hook`; `CMD` follows the one hook-command rule shared with the config (Config, Characters): at most 4096 characters, no control character other than newline and tab, no Unicode format (Cf), line or paragraph separator (Zl, Zp) or surrogate character, and at least one character that is not whitespace, a space separator or invisible (U+2800, U+115F, U+1160, U+3164, U+FFA0); the hook runs with timeout 30 and `async: true`. `--pr` together with `--repo` is exit 2 `usage` (`details.kind: bad_combination`). `polled` (with `--pr`) is true when that PR's snapshot committed; a failed, locked, discarded, deferred, paused or merged PR is `polled: false`. Exit 0 when the poll ran, including `already_running` and a partial result where every failed object was classified. Exit 12 as defined in Failures; a `--pr` that names no stored PR is exit 10 `not_found` before forgectl is touched; forgectl's own `config_invalid` on a host call ends the cycle (no further listing, no snapshot) with the report and exit 12. `poll` is safe to run concurrently; a poll whose every needed snapshot is locked exits 0 with `already_running` (Locks and commit).

### `list`

`pr-watch list [--label k=v]... [--owner O] [--pr <ref>] [--status active|terminal|unreachable]`

Prints the watches (id, kind, key or reference, owners, labels, `created_at`, and for a query watch the member count, `enumerated_at` and `pending_baseline`), the PRs (canonical `pr`, `pr_id`, status, state, draft, `ci_state`, `ci_head_sha`, `ci_stale`, `ci_stuck`, `head_sha`, `last_polled_at`, `last_full_at`, `incomplete`, `incomplete_snapshots`, failure count, `terminal_at`, `terminal_kind`, `baselined_at`, `baselined`, sources), `last_poll_finished_at` (time of the last unrestricted `poll` that ran to its end and observed at least one listing or snapshot, null if never) and per host `paused_until`, `last_enumerated_at`, `last_full_at`. Never contacts a host. `--status` filters PRs only; `--owner` and `--label` select watches, and the PRs shown are those with at least one source among the selected watches; `--pr` selects one PR (a name or URL that is not stored selects nothing: exit 0 with empty `prs`, unlike `show`, which exits 10; a name that matches more than one stored row is exit 2 `ambiguous_reference`) and does not narrow `watches` or `hosts`; watches are ordered by `created_at` then id, PRs by `pr` then `pr_id`, hosts by name; repeated `--label` is ANDed (with `--owner`, over that owner's own labels); `hosts` lists every row of `hosts`. `enumerated_at` of a query watch is derived: the oldest `hosts.last_enumerated_at` over the hosts the watch lists, null while any is null or older than the watch's `created_at`, and always null for an unfiltered query (no `--host` or `--repo`: the hosts it covers are every host in scope, which no stored value lists); `pending_baseline` is the number of its members with no digest.

### `show`

`pr-watch show <pr>`

One watched PR: its row, its watches and the digest summary (the same fields as in `list`, plus `blocked_by`, `review_decision`, `approvals_at_head`, the reviewers' latest states, and the counts in `seen`) and its most recent 20 events, oldest first. Exit 10 when the PR is not stored. `<pr>` is matched on the canonical `pr`, a URL or the `pr_id` of a stored row (Identifiers); each reviewer is printed with its reviewer `key`. A reviewer whose stored state is `unknown` is not listed (it counts as no entry); `at` is printed as UTC microsecond text. `show` prints stored rows only: a PR that only has retained events is exit 10 (`events --pr` still resolves it).

### `events`

`pr-watch events [--label k=v]... [--pr <ref>]... [--type T]... [--since CURSOR] [--limit N]`

Prints events after the cursor, oldest first. Never contacts a host and never changes state (non-destructive: each consumer keeps its own cursor). Without `--since`, no event is returned and the cursor is the current head ("from now"). The result carries `events`, `cursor`, `gap`, `more` and `last_poll_finished_at` (time of the last `poll` that ran to its end and observed at least one listing or snapshot, null if never, so a consumer can tell "quiet" from "not polled"). `--limit` defaults to 100 (maximum 1000). `--label` is an AND filter over the labels stored on the event, and the three filter kinds (`--label`, `--type`, `--pr`) are ANDed with each other; `--type` is repeatable (OR); `--pr` is repeatable (OR): a reference is resolved through stored rows first; if no row matches, through the `pr` and `pr_id` columns of stored events (an event whose `pr` equals the reference supplies its `pr_id`, and then all events of that `pr_id` are returned, whatever name they were detected under), so a PR whose row expired still resolves while its events are retained. With repeated `--pr` an unresolvable reference is skipped, and exit 10 only when none resolves.

- `seq` is an AUTOINCREMENT integer (deleted numbers are never reused). `meta.pruned_through_seq` is the highest deleted seq. `gap` is true iff the cursor's `store_id` differs, or its `seq` is greater than the head, or its `seq` is less than `pruned_through_seq`; a cursor equal to `pruned_through_seq`, or at the head after a quiet month, is no gap, and a cursor at 50 with an empty table and head 100 is a gap. The head is the AUTOINCREMENT high-water mark (`sqlite_sequence`), 0 on a new store. The head and the rows are read in one read transaction.
- `cursor` in the result is the head read in that transaction when `more` is false (everything up to it was examined, so filters do not rescan), and the `seq` of the last returned event when `more` is true. With a gap and a backlog the same rules apply and the filters apply to the backlog. With a gap, the events from the oldest retained one are still returned (all of the current store when the id differs); the consumer must re-sync current state through forgectl and treat the events as possibly incomplete.
- With no store at all (no state directory, no `state.db`, or an empty file) `events` creates nothing and reports an empty store: head 0 and the placeholder `store_id` `aaaaaaaa`, so a cursor of another id is a `gap`. A consumer that took that cursor before the first `watch add` sees one `gap` afterwards; the `cursor` of the `watch add` result avoids it. A cursor with another `store_id`, or above the head, reads from the start of the store; one below `pruned_through_seq` reads after its own seq. `rev` is not an output of any read command, so a rename changes nothing `events`, `show` or `export` print.
- A stored event that cannot be read back (a payload that is not a JSON object, labels that are not a list of strings) is exit 1, `code: internal`, with a fixed message naming its `seq`; the same applies to `show` and `export`.
- `--limit` outside 1 to 1000, an unknown `--type`, an invalid `--label` or a bad cursor is exit 2 (`code: usage`, `details.kind`: `bad_limit`, `bad_type`, `bad_label`, `bad_cursor`).
- Output without `--json` is human text with no stability guarantee; tests and consumers use `--json`.

### `label`

`pr-watch label add <pr|--watch ID> k=v... [--owner O]` and `label remove <pr|--watch ID> k=v... [--owner O]`

Adds or removes labels on a watch (a watch is named by its id, or by a per-PR watch's reference), owned by the owner (Identifiers). `label add` needs the owner to hold a reference (else exit 10, `details.kind: owner_not_held`) and a watch (a PR with no per-PR watch: exit 10, `details.kind: no_watch`); adding a label the owner already has is a no-op. A watch carries at most 64 labels, counted as the union over its owners: a `label add` that would leave the union above 64 is refused before anything is written (exit 2, `code: usage`, `details.kind: too_many_labels`, with `details.limit` 64 and `details.count`); a label that is already present (from any owner) does not count again, so re-adding at the cap is a no-op success. `label remove` is idempotent like `watch remove`: an absent label (`reason` null, `watch` the unchanged watch), an owner that holds no reference, or a PR with no watch is exit 0 with `changed: false` (and `reason: not_held` or `no_watch` where it applies, with `watch` null), without taking the write lock; `label add` keeps exit 10. Labels already stored on past events do not change.

### `prune`

`pr-watch prune [--dry-run]`

Deletes events older than `retention.events`, rows past `expiry.after_terminal`, and the watches and members that only referred to them (so expiry happens up to a day after `expiry.after_terminal`; the expiry predicate is evaluated per row inside the deleting transaction, PR status), and deletes leases that are expired, whose holder is dead, or whose PR has no row (even when the holder is alive; all counted as `leases_deleted` in the result). It also runs at most once a day at the end of `poll`, and runs `PRAGMA wal_checkpoint(TRUNCATE)` with `busy_timeout` set to 0 around it (restored after), so a reader holding a snapshot never makes it block writers; a busy checkpoint is ignored and retried by the next `prune` or `poll`. `prune --dry-run` is read-only like `list`: it opens the store read-only, creates nothing, treats a missing store as empty, writes no `log.jsonl` record and does not stamp `last_prune_at`. Retention advances `pruned_through_seq` (never lowers it), so a cursor below it reports a gap (Events) even if an earlier `prune` ran with a later clock.

### `cron`

`pr-watch cron install [--every D] [--dry-run]` and `cron uninstall [--dry-run]`. `cron install` writes one tagged block (paths are written single-quoted by pr-watch; the `. '<env_file>' &&` part is present only when `cron.env_file` is set):

```text
# pr-watch managed v1 every=5m
PATH=<dirs>
*/5 * * * * . '<env_file>' && '<absolute pr-watch>' poll --quiet
# pr-watch managed end
```

A block starts at a line that is exactly `# pr-watch managed` or begins with `# pr-watch managed` followed by a space and ends at the next `# pr-watch managed end` line. A block whose end line is missing is never removed or replaced automatically: `cron install` and `cron uninstall` leave the crontab unchanged and exit 2 `usage` with the hint to remove it by hand. `previous_every` is null when the first line has no `every=`. The block has one entry. `--every` wins over `poll.interval_hint`; accepted forms: `Nm` where N divides 60 (`*/N * * * *`; `60m` is hourly) and `Nh` where N divides 24; anything else is exit 2. Validation: refuse any value containing a newline, `%`, quotes or `;`; paths without whitespace; `PATH` holds `~/.local/bin` and the absolute directory of the resolved `forgectl` only if it is owned by the user or root and not group- or world-writable; `cron.env_file` must be a regular file (not a symlink) owned by the user with no group or world permission bits, in a directory owned by the user and not group- or world-writable. The crontab read-modify-write holds an `flock` on `state/cron.lock` and re-reads before writing. The result prints `replaced` (true when a block existed and was replaced), `changed` (true when the crontab text changed; re-installing an identical block is `replaced: true`, `changed: false`), `previous_every` and `warnings`: `cron install` warns on stderr and in `warnings` when a `pr-watch poll` line exists outside the block. `--dry-run` runs the same read and the same computation as a real run and only skips the write: it reads the crontab once (`crontab -l`), never writes it, takes no `cron.lock` and creates no state directory or file; every refusal of the real run (malformed block, bad `--every`, bad `cron.env_file`, unsafe path, unreadable crontab) applies unchanged, and the stderr warnings are still printed. Its `changed` is what a real run against the same crontab would report. Both commands print `dry_run` (true for `--dry-run`, else false) and `block`: the lines the real run writes (`install`, the same as `lines`) or removes (`uninstall`, from the start line to the end line; the lines are verbatim from the crontab but decoded as UTF-8 with replacement, so undecodable bytes become U+FFFD, and a CRLF line keeps its trailing `\r`), and `null` when nothing changes. `--json` prints the block as the `block` array (and `lines` for `install`); without `--json` the human output prints the block lines after a `dry run: would ...` line. The result of a real run carries the same two members. Between a dry run and a real run the crontab can change, so a dry run is a preview, not a promise. The harness's `awkit cron install` writes the same block and each replaces the other's.

Details of `cron` that the paragraph above leaves open:

- **Malformed crontab.** Any block that is not exactly one start line followed by one end line is refused untouched by both commands (exit 2 `usage`, `details.kind: malformed_crontab`); the message names the shape (no end line, an end line without a start line, more than one block or a second start line, an end line before its start line) and says to repair or remove the block by hand.
- **Paths.** A bad or relative `cron.env_file` is `config_invalid` (exit 2) and its value is never echoed. A path of `pr-watch` that cannot be written is `usage` with `details.kind: unsafe_path`. The characters refused in a path are wider than the sentence above: shell and cron metacharacters (quotes, `%`, `;`, `\`, `$`, `&`, `|`, `<`, `>`, brackets, braces, `*`, `?`, `!`, `#`, `^`, backtick) and the Unicode categories Cc, Cf, Zs, Zl, Zp and Cs. A block line is at most 999 bytes (vixie cron and cronie read a line into a 1000-byte buffer with its terminator): a longer entry line is `config_invalid` when `cron.env_file` makes it too long, else `usage` (`unsafe_path`), as is a longer `PATH=` line.
- **`PATH=`.** The line holds `~/.local/bin`, then the directory of `forgectl`, then `/usr/local/bin:/usr/bin:/bin` (the system directories are written without checks). An unsafe directory is left out with a warning; so is a directory containing `:` (it would split the line; `:` stays allowed in the `cron.env_file` path), and a `forgectl` found only through a relative `PATH` entry. The warnings also say when `forgectl` is not found. The harness must write the same `PATH=` tail for the blocks to be byte-identical.
- **Schedule.** `Nm` is `*/N * * * *` (`1m` is `* * * * *`, `60m` is `0 * * * *`); `Nh` is `0 */N * * *` (`1h` is `0 * * * *`, `24h` is `0 0 * * *`). `every=` in the header is stored as given.
- **Poll-line warning.** The check for a `pr-watch poll` line outside the block is a heuristic: comment lines are ignored, and `poll` must be followed by whitespace or the end of the line.
- **Dry run.** `--dry-run` is a read-only form like `prune --dry-run`: no `cron.lock` (the lock only orders writers, and one `crontab -l` is a consistent snapshot) and nothing is created under the state directory, so it also works when that directory does not exist yet. A dry run logs nothing, config warnings included.
- **crontab program.** `crontab` runs with `LC_ALL=C`. An empty result is installed with `crontab -r`. Bytes outside the block are kept; the only change is a final newline when the table would otherwise not end in one (cron refuses such a table, so an install followed by an uninstall cannot restore a missing final newline). A crontab larger than 1 MiB or containing a NUL byte, a failing or timed out `crontab`, a lock held for more than 30 seconds, a table that does not read back as written and a table that keeps changing are exit 1 `internal`; the messages carry the exit code and never `crontab`'s own text. A real run of either command creates the state directory and `cron.lock`, a dry run creates neither; `cron uninstall` ignores the config.
- **Limits.** Only the direct parent directory of `cron.env_file` and the directory of `forgectl` are checked, and between the check and cron's use of them they can change (accepted). A `crontab -e` by a tool that does not take `cron.lock`, between the re-read and the write, can be overwritten (accepted; a changed table at read-back is reported as an error). The entry is `. '<env_file>' && ...` and needs a POSIX `sh`: a foreign `SHELL=` line earlier in the crontab can break it.

### `export`

`pr-watch export [--since D] [--label k=v]... [--type T]... [--pr <ref>]...`

Prints the stored events oldest first as JSON lines (each `schemas/event.json`), always JSON whatever the global flags. `D` is a duration (Time) and selects events detected within the last `D` (without it, every retained event); the three filters are those of `events` (a human who wants "what happened overnight" runs `export --since 1d`). `--since 0` selects nothing; `export` has no limit, and `--quiet` does not silence it. pr-watch takes no external action, so it writes no `audit.jsonl` and `export` has no audit records to print.

### Global flags

`--json`, `--config PATH`, `--verbose`, `--quiet`, `--version`. `--quiet` suppresses the human-readable result on stdout (with `--json` the document is still printed) and informational stderr lines such as the `log.jsonl not written` notice; it never suppresses an error or a warning about the input (the `pr_unknown` warning of `watch remove`). `--dry-run` exists on `prune`, `cron install` and `cron uninstall` (read-only previews, see each command); `watch add` and `watch remove` do not take it (they write only local state). `--yes` and `--actor` are not accepted: no command takes an external action or asks for a confirmation. `--verbose` together with `--quiet` is a usage error (exit 2, `details.kind: conflicting_flags`). Flag abbreviations are not accepted. Usage errors never echo argument values: a message names our own options and choices, and counts unrecognized arguments (`unrecognized arguments (2)`) instead of printing them.

## Exit codes

| Code | Meaning |
|---|---|
| 0 | success (including `already_running`, a no-op, an idempotent removal and a clean partial poll) |
| 1 | unexpected or internal error |
| 2 | usage error (bad flag, bad cursor, invalid PR reference, invalid config, owner required) |
| 10 | not found (PR not stored or not watched, no watch to label, PR missing on the host) |
| 12 | failed for a reportable reason (host unreachable or failing and a whole host failed leaving scopes unlisted, forgectl missing or too old, a forgectl result violating the contract in a direct command's single call (during a poll the same violation is a per-PR failure, exit 0; Failures), store too new, state unsafe) |
| 20 | refused (a forgectl refusal passed through, for example `unknown_host`, with its `reason` and `lower_error`) |

Codes 11, 13 to 19 and 21 are unused: pr-watch has no pre-hooks, no pending store and no session. A signal ends the process with 128 plus its number, for every command, with no traceback (Signals). A closed or failing stdout (a closed pipe, `/dev/full`, a closed fd 1) is exit 1 with one stderr line `cannot write to stdout` and no envelope: the one exception to the envelope rule above, since there is nowhere to print it. The command's writes had already committed.

## Output by exit code

- **0:** the command's result object (`schemas/cli/<command>.json`); with `--json` always valid JSON on stdout.
- **12 from `poll`:** the normal poll report (`failed` lists what was left unchecked) and, on stderr, one line per error. Exit 12 for forgectl missing or too old, `store_too_new` or `state_unsafe` prints the error envelope instead.
- **Any other non-zero exit:** the error envelope on stdout (and a text line on stderr).

### Error envelope

`{"error": {"code": "...", "message": "...", "reason": "...", "details": {...}, "lower_error": {...}}}` (`schemas/cli/error.json`). `code` is one of `usage`, `config_invalid`, `invalid_pr`, `not_found`, `host_failed`, `tool_missing` (with `details.install`), `tool_too_old` (with `details.required` and `details.found`), `contract` (a forgectl result violated the documented shape; per call, never exit 12 for a poll alone), `store_too_new` (a database from a newer version, exit 12), `state_unsafe` (exit 12, Files), `refused` (with `reason`), `internal`. `lower_error` carries forgectl's own `code`, `reason`, `retry_after` and `message` when a forgectl call caused the error. Messages are sanitized one-line text.

### Result objects

The result objects of `watch add`, `watch remove`, `label add|remove`, `prune`, `cron install|uninstall`, `list` and `show` are defined by `schemas/cli/<command>.json`, which are normative for their field names. Rules that go beyond the schemas: every mutating command prints `changed` (true or false); a PR stored without a digest (added with `--no-baseline`, not yet polled) prints `null` for `state`, `draft`, `ci_state`, `head_sha` and `last_polled_at`; `events.more` is always present; a `poll` that exits 0 with `already_running` prints the full report shape; only `prs.skipped_locked` can be non-zero.

### Poll report

`poll --json` prints: `already_running`, `started_at`, `duration_ms`, `hosts`, `prs`, `events`, `hooks`, `failed`, `full_pass`, `truncated`, `deferred` and, with `--pr`, `polled`. Definitions:

- `hosts.<h>`: `queried` (a listing was made), `snapshots` (committed snapshots; `requests_estimate` is that number times 7 or 21), `skipped` (`no_credential`, `not_in_scope` or null), `incomplete_listing`, `paused_until`, `last_full_at`, `requests_estimate` (Pacing and backoff), `errors` (an array of `{code, pr, retry_after}`: the listing and whole-host errors of the host, `pr` null; per-PR failures are in `failed` only).
- `prs`: `snapshotted` (successful snapshots), `unchanged` (snapshots that produced no events), `skipped_locked`, `skipped_conflict`, `unreachable` (PRs that became unreachable this cycle), `incomplete` (Digest: a database-wide current count, not per cycle; `post-poll` `degraded` likewise).
- `events`: counts by type, zero-filled over all twelve types in the event order. `hooks`: `run`, `skipped` (hooks skipped by a cap or by the drain bound), `failed` (runs that exited non-zero, timed out or failed to spawn). `failed`: the PRs, scopes or hosts left unchecked, each with the failure code; `ref` is as defined in Failures. `full_pass` is true when any host did a full pass. `truncated` is true when `poll.max_duration` or `poll.max_snapshots` stopped new snapshots, and `deferred` counts the snapshots not started because of either bound. `polled` is whether the `--pr` PR was refreshed. With `already_running` only `prs.skipped_locked` can be non-zero: `deferred` is 0 and `truncated` and `full_pass` are false. A host named in `failed` (a failed `whoami` that names no host has `ref` `whoami`) can have no entry in `hosts`.
- `list` and `show` rows carry `last_polled_at` (a row's last committed snapshot) and `last_full_at` (the host's, copied).

Exit codes are in [Exit codes](#exit-codes) (what a poll does with each outcome is in [Failures](#failures)). Golden poll reports are part of the test suite.

## Hooks

Hook points (design guide section 8). All are post-hooks that report a change that already happened: they cannot veto, escalate or undo anything, and their failures are logged and warned, never fatal ("warned" means a warn-level `hook_run` record in `log.jsonl`; no line is printed on stderr).

| Hook | Fires | Payload |
|---|---|---|
| `on-opened`, `on-reopened`, `on-pushed`, `on-comment`, `on-review_comment`, `on-review`, `on-approved`, `on-changes_requested`, `on-ci`, `on-ready`, `on-merged`, `on-closed` | once per stored event of that type, after its transaction committed (never from `watch add`) | the event (Events) plus `tool`, `hook`, `object_type: pr`, `object_id` (the `pr_id`) and `event_id` |
| `post-poll` | once at the end of a `poll` that had a failed object (other than an already `unreachable` PR), a host error or a newly unreachable PR (Poll cycle, step 8) | counts (excluding itself), per-host error codes (from `hosts.<h>.errors` and from `failed` entries of kind `host`, which may have no `hosts` entry), `degraded`, `unreachable` (pr, pr_id, code), no host text; its `object_id` is the poll's `started_at` |

- **Delivery** is at-most-once. Events are committed first; hooks run afterward, one invocation per event. If `poll` is killed, the events are safe but their hooks are not re-run; a consumer that needs a guarantee reads `events` with a cursor. The payload carries `event_id` (the same value as the event's `id`) as the deduplication key.
- **Timing.** After each PR's transaction commits, its hooks are queued in event order. A pool of `hooks.concurrency` workers (default 4) runs them while snapshots continue; the poll exits after the pool drains, and each hook is bounded by its timeout (`hooks.<name>.timeout`, 1 to 600 seconds, default 30). Hooks that are exempt from the caps (Cap) are queued ahead of the others. After `poll.max_duration` plus 2 minutes from the poll's start no further non-exempt hook is started (the rest are skipped with a `hook_cap` record); exempt hooks are still started and are bounded by their timeout. At a hook's timeout its process group gets SIGTERM, then SIGKILL after 5 seconds, only while its leader is unreaped; after SIGKILL the pool waits at most 5 more seconds, then abandons the slot and writes `hook_run` with `exit_code: null` and `timed_out: true`. Only the hook's leader process is bounded: a hook must not leave background work. `async: true` (the default) means "in the pool, concurrently with other hooks"; `async: false` means one at a time, in queue order across PRs, never concurrently with another `async: false` hook of the same poll process (two polls can overlap, and then two such hooks can run together); `async: true` hooks are never held back by it. Hook results are ignored. Order across hooks of one PR is queue order only for `async: false`; consumers order by `seq`.
- **Process.** `sh -c`, own session, stdin a pipe (pr-watch ignores SIGPIPE and writes the payload without blocking the coordinator, with a deadline), stdout and stderr to `/dev/null`, `close_fds`, cwd a private directory `<state dir>/hooks-cwd` (mode 0700, created if missing; it starts empty but pr-watch never cleans it, so files a hook leaves there accumulate and the hook author owns that), non-absolute `PATH` entries dropped from the hook environment, no template substitution. A hook never receives untrusted text on argv or in the environment.
- **Environment.** Clean: `PATH`, `HOME`, `LANG`, `TERM`, `XDG_*` (`HOME` and each `XDG_*` only when its value is an absolute path; an unset or relative `HOME` is replaced by the account's home directory from the password database, and a relative `XDG_*` is dropped), `PR_WATCH_HOOK=<hook>`, `PR_WATCH_ID=<object id>` (the `pr_id`; for `post-poll` the poll's `started_at`), `PR_WATCH_EVENT_ID=<event id>` (empty for `post-poll`), `PR_WATCH_OBJECT_TYPE` (`pr` or `poll`), plus names in `hooks.env_allow`. They never include forgectl's token variables unless a name is listed in `hooks.env_allow`. This is stricter than design guide section 8 (which says hooks inherit the environment minus token variables); the deviation is intended.
- **Cap.** At most `hooks.max_per_poll` (default 50; 0 means no hook runs) hook invocations start in one poll, and at most `hooks.max_per_pr_per_poll` (default 10) per PR, so a flooded PR cannot use the whole budget. `merged`, `closed` and `post-poll` hooks are not counted and never skipped by either cap (decided by the hook's name, whether it is configured or added with `--hook`) (there is at most one `merged` or `closed` per PR and one `post-poll` per poll). The rest are skipped; one `hook_cap` log record names the number skipped and, when any skipped hook belongs to an event, the first and last such event ids (a skipped `post-poll` has none, so a record for skipped `post-poll` hooks alone carries the count only); the report counts them in `hooks.skipped`; their events are stored.
- **Logging.** Every hook run writes a `hook_run` record (event id, hook, exit code or null, `timed_out`, duration). `post-poll` and `--hook` runs are hooks; the cap and its exemptions apply by hook name to every run, whatever its origin.
- **Interpretations.** `hooks.max_per_poll: 0` runs no hook at all, the exempt ones included (they are skipped and counted). A hook killed by a signal is logged with `exit_code` 128 plus the signal number. The caps count a hook when it is queued; a capped hook, one skipped by the drain bound and one whose payload could not be encoded each get their own `hook_cap` record (with its own message). `hooks-cwd` is verified once, on the first hook; when that fails every hook of the poll fails (logged, `exit_code: null`). A hook stopped by a poll's shutdown signal writes no `hook_run`. `post-poll` is not sent for an `already_running` poll with no failure. When a tool error ends the poll (exit 12 `tool_missing` or `tool_too_old` during snapshots), the hooks of events already committed still run to the end (the error envelope is printed after the pool drains), `post-poll` does not fire and no hook counts are reported (the envelope has no report).
- **Hook authors.** Never interpolate payload fields into a shell command line or a template; use `jq -r ... | tool --stdin`. A hook receives labels and watch ids in the payload and filters on them itself.
- **Deviations from the design guide.** (1) `async: true` means "in the pool, concurrently", and the poll waits for the pool (guide section 8: detached); (2) hook stdout goes to `/dev/null`, so no `decision_id` or JSON stdout is read; (3) the environment is cleaner than guide section 8 (Environment).

Payload shapes are in `schemas/hooks/<hook>.json`; the event object is `schemas/event.json`. Every field that carries host text (`author.login`, `reviewer.login`, `path`, check names, `blocked_by.detail`) is marked `x-untrusted`.

## Config

File `~/.config/pr-watch/config.yaml` plus `config.d/*.yaml` (design guide section 5). Keys (schema `schemas/config.json`, example `config.example.yaml`; every value shown is the default, and unset keys use the stated built-ins):

```yaml
poll:
  interval_hint: 5m        # the cron install default only (the `--every` forms: Nm with N dividing 60, Nh with N dividing 24)
  # full_every: 6          # cycles between full passes, per host; unset: 6 on GitHub, 12 on GitLab
  # concurrency: 4         # snapshot workers per host; unset: 4 on GitHub, 2 on GitLab
  host_low_water: 100      # forgectl rate_limit.remaining below this: snapshot only what must be (0 to 1000000)
  overlap: 60s             # subtracted from the host-time watermark of a per-PR repo scope (covers search index lag)
  hosts_ttl: 1h            # how long whoami's host list is cached
  max_duration: 15m        # the cycle stops starting snapshots after this (at least 1ms; 0 is config_invalid)
  max_snapshots: 40        # snapshots started per host and cycle; deferred ones keep their triggers (0 to 1000; 0 is unlimited)
hosts: {}                  # per-host overrides, for example {github.com: {full_every: 12, concurrency: 2}}
retention:
  events: 30d              # at least 30d
expiry:
  after_terminal: 7d
failures:
  unreachable_after: 5
detect_force_push: false   # call forgectl compare to fill `forced`
ci:
  settle_polls: 1
  pending_max_age: 6h      # an unsettled PR is snapshotted every cycle for at most this long
forgectl:
  timeout: 120s            # forgectl --timeout per call (at least 1ms; a zero value is config_invalid)
  max_output_mib: 32       # bytes of stdout of one forgectl call, in MiB (1 to 256)
hooks:
  max_per_poll: 50         # 0: no hook runs
  max_per_pr_per_poll: 10  # 1 to 1000
  concurrency: 4           # 1 to 32
  env_allow: []
  # on-approved: [{cmd: "...", timeout: 30, async: true}]
cron:
  env_file: null
repos: {}                  # per-repo overrides (design guide section 5), for example {github.com/o/r: {detect_force_push: true, ci: {settle_polls: 2}, failures: {unreachable_after: 8}}}
```

A section (`poll`, `hosts`, `hooks`, ...) must be a mapping: a section written with no value (YAML null, for example `hosts:` followed only by comments) is refused as `config_invalid`, so write `hosts: {}`. A hook's `timeout` is an integer number of seconds (1 to 600); every other duration is a string (`5m`, `30d`) of at most 9 digits and at most `3650d` (ten years), else `config_invalid` naming the key. File and environment integers are plain decimal: `-?0` or an optional `-` and digits without a leading zero, at most 18 digits (no `+`, `_` or hexadecimal). `retention.events` below `30d` (or not a whole number of days) is invalid config (exit 2, `code: config_invalid`), not clamped. `poll.interval_hint` accepts only the `--every` forms (`Nm` with N dividing 60, `Nh` with N dividing 24), else `config_invalid`. `forgectl.min_version` is not a config key (`MIN_FORGECTL` is a constant of the release). `me.name` is an optional key (the default owner's name). Built-in per-host defaults when not set: `full_every` 6 on GitHub and 12 on GitLab, `concurrency` 4 on GitHub and 2 on GitLab (backend from `whoami`). Per-repo overrides apply to `detect_force_push`, `ci.settle_polls` and `failures.unreachable_after`. The identity ("me") is forgectl's: set `me` and `hosts.<host>.me` in forgectl's config (setting `hosts.<host>.me` saves one request per snapshot on GitHub); pr-watch has no `me` key of its own, apart from `me.name` used for the default owner. Invalid config fails fast naming the key. pr-watch holds no credentials: git-host access is forgectl's.

- **Files.** `--config PATH` replaces `config.yaml`; the drop-ins are read from the `config.d` directory beside that file. A missing default file means the built-in defaults; a missing `--config` file is exit 2 `config_invalid`. In `config.d` dotfiles and names not ending in `.yaml` are skipped and the rest are read in bytewise order. Limits (exit 2 `config_invalid`): 256 KiB per file, 1 MiB for all files together, 256 drop-in files. A symlinked file or `config.d` is followed and the ownership and mode checks apply to the target, on the open file; the parent directory (`~/.config/pr-watch`) is not checked.
- **Merging.** Maps merge; hook lists (`hooks.<name>`) append across files and a later file cannot clear them; every other value, `hooks.env_allow` included, is replaced by the later file. Each file is validated alone, then the merge with the environment as a whole.
- **Bounds.** `poll.max_duration` at least 1ms (a zero or non-positive value is refused as `config_invalid` naming the key: it would make every snapshot stage start out of time, so it is not read as "no limit"; use a long duration for that), `poll.full_every` 1 to 10000, `poll.concurrency` 1 to 64, `poll.host_low_water` 0 to 1000000, `failures.unreachable_after` 1 to 1000, `ci.settle_polls` 0 to 10, `hooks.max_per_poll` 0 to 100000, `me.name` 1 to 128 characters, `cron.env_file` 1 to 4096 characters, a hook `cmd` 1 to 4096 characters. A `hosts` key is a lowercase host (`[:port]`) and a `repos` key a repo id, both as in Identifiers; a malformed key is `config_invalid`.
- **Characters.** `me.name`, `cron.env_file` and hook commands refuse control characters (C0, DEL and C1); a hook `cmd` may contain newline and tab and must contain a non-blank character. `--hook` and a config `cmd` share one rule: besides control characters, the Unicode categories Cf, Zl, Zp and Cs are refused, and at least one character must be neither whitespace, a space separator (Zs) nor one of the invisible U+2800, U+115F, U+1160, U+3164, U+FFA0 (so a command of only U+00A0, U+3000 or U+2800 is refused).
- **Repo ids match case-insensitively** (host and path, as in Identifiers): `repos` entries are found whatever the case of the repo id, and two `repos` keys that differ only in case are `config_invalid` (naming the key), also across files.
- **`me.name`** is `null` in the loaded config when unset; the code that resolves the owner applies the OS-user fallback and the cleaning rule (Identifiers, Owner).
- **Precedence:** `repos.<id>` and `hosts.<h>` entries, then `PR_WATCH_*` environment, then the config files (`config.d` after the main file), then built-ins; no CLI flag overrides a config key (only `--hook` adds a hook).
- A config file, a `--config` file or the `config.d` directory owned by another user or writable by group or others is refused when it is loaded (exit 2 `config_invalid`).
- `hooks.env_allow` names starting with `PR_WATCH_`, `LD_` or `DYLD_` in any letter case are rejected (`config_invalid`); names containing `TOKEN`, `SECRET`, `KEY` or `PASSWORD` produce a `config_warning`.

## Environment variables

Config keys may be set as `PR_WATCH_<KEY>` (nested keys joined with `__`, for example `PR_WATCH_POLL__CONCURRENCY`). Only scalar keys of `poll`, `retention`, `expiry`, `failures`, `ci`, `forgectl`, `detect_force_push`, `hooks.max_per_poll`, `hooks.max_per_pr_per_poll`, `hooks.concurrency` and `me.name` can be set this way; never `hooks.<name>` lists, `hooks.env_allow`, `cron.*`, `hosts` or `repos`. Booleans are `true` or `false`, integers plain decimal as in the file (Config), durations as in the file. The file-only keys (`PR_WATCH_HOOKS__*`, `PR_WATCH_CRON__*`, `PR_WATCH_HOSTS__*`, `PR_WATCH_REPOS__*`) are ignored when set as variables, with a `config_warning` whose `key` is the variable name. `PR_WATCH_HOOK`, `PR_WATCH_ID`, `PR_WATCH_EVENT_ID` and `PR_WATCH_OBJECT_TYPE` are set for hooks only, are not config keys and are ignored by the loader (so a hook that runs `pr-watch` is not confused); any other unknown `PR_WATCH_*` name is ignored with a `config_warning` record. pr-watch passes its own environment through to forgectl unchanged (forgectl reads its token variables from it); `FORGECTL_GH_BIN` and `FORGECTL_GLAB_BIN` therefore apply. A required variable that forgectl needs and is missing surfaces as forgectl's `auth_required`.

## Audit and log

pr-watch takes no external action, so it writes no `audit.jsonl`. `log.jsonl` (`schemas/log.json`) is a public, append-only record of polls (start, end, per-host summary), snapshot failures, state changes of a PR (`status` transitions), hook runs (event id, hook, exit code, duration), `hook_cap`, `part_incomplete`, `commit_skipped`, `events_dropped`, `labels_capped`, host failures and configuration warnings; it never holds host text beyond the one-line fields. `log.jsonl` rotates at 10 MiB, keeping 3 files. A `snapshot_failed` record is written for the first failure of a streak, when its code changes, and when the count reaches a multiple of `failures.unreachable_after`; hook runs and `part_incomplete` are one record each. The event stream itself is the product: it lives in `state.db`, is read through `events`, and `export` prints it.

`commit_skipped` (implementation reading): written with `pr_id` and a `reason` when a snapshot commit was discarded (`revision`, `source_removed`, `newer_listing`). `events_dropped` (level `warn`, implementation reading): written with `pr`, `pr_id`, `count` and `reasons` (the distinct reason codes, sorted) when a committed snapshot detected events that could not be stored (Events, Dropped events). `labels_capped` (level `warn`, implementation reading): written with `pr`, `pr_id`, `kept` (256) and `total` when the label union of a snapshot's events exceeded 256 and was cut to the first 256 in sorted order; a snapshot without events writes none.

Writing rules (implementation readings). A record is one ASCII JSON line written with a single `write` to a file opened append-only and without following symlinks; a log file that is not a regular file, is owned by another user or is group- or world-writable is not written (a symlink is never followed). Control and bidi characters in a text field become `<U+XXXX>` markers and free-text fields are cut to their schema length; an identifier (`pr`, `pr_id`, ...) or number that does not match the schema is never cut or coerced: the record is dropped. Rotation shifts `log.jsonl.1` to `.3` under an exclusive `flock` on the state directory, taken without blocking and retried for about a second (then rotation is skipped and the record is appended anyway). Rotation is best-effort under concurrent rotation: a record may be lost, the log is never corrupted, and at most 4 files exist. A short write leaves a newline-terminated fragment, so consumers must skip a line that does not parse. A failure to write (disk full, read-only filesystem, a refused file, an invalid record) never changes a command's result or exit code: pr-watch prints one `pr-watch: log.jsonl not written: <reason>` line on stderr (not with `--quiet`) and goes on. Configuration warnings are written as `config_warning` records at the start of every command except `list`, `show`, `events` and `export`, so a consumer that reads often cannot fill the log with one warning.

## Files

- `~/.config/pr-watch/config.yaml`, `config.d/*.yaml`.
- `~/.local/state/pr-watch/state.db`: private (SQLite, WAL, versioned additive migrations); the tables are listed in State. No alias table is needed (Identifiers).
- `~/.local/state/pr-watch/log.jsonl`: public, with the rotated `log.jsonl.1` to `log.jsonl.3`.
- `~/.local/state/pr-watch/cron.lock` and `~/.local/state/pr-watch/hooks-cwd/` (the empty working directory of hooks).
- pr-watch creates directories with umask 077 (directories are mode 0700, files 0600); missing parent directories of the state directory are created mode 0700, and only the final component of the state directory is refused as a symlink (a parent may be a symlink). `XDG_STATE_HOME` is used only when absolute, and `HOME` only when absolute (else the passwd home directory). `hooks-cwd` is created (0700) and checked at start (when it is missing and cannot be created because the filesystem is read-only or access is denied, the start continues and the hook runner creates it, or fails there), and `cron.lock` is checked at start when it exists. One rule for refusals: the state directory, `hooks-cwd`, `state.db`, the log directory and `cron.lock` are checked on start, and one not owned by the user, group- or world-writable, or a symlink is refused (exit 12, `code: state_unsafe`); the config file, `config.d` and a `--config` file are checked when loaded and refused with exit 2 `config_invalid` (Config). `-wal` and `-shm` inherit the database mode. Read-only commands (`list`, `show`, `events`, `export`, and `prune --dry-run`) create nothing: when the state directory or `state.db` does not exist they behave as on an empty store and create no directory or file (not even `hooks-cwd`); an existing state directory and `state.db` get every check above, so `store_too_new` and `state_unsafe` still apply. Read-only commands also never write the store: they open `state.db` with a `mode=ro` URI, `PRAGMA query_only=ON` and one `BEGIN ... ROLLBACK` read transaction, and never switch the journal mode, migrate, take the write lock or checkpoint (so they work on a read-only file and never rewrite a 0-byte `state.db`, which with no tables and `user_version` 0 is an empty store). SQLite itself may give a read-only reader of a WAL database an empty `-wal` and a `-shm` when the directory lacks them; the database file and an existing WAL are never changed. When the directory is read-only and holds no `-shm` for a WAL database, SQLite cannot open it read-only: the command is refused (exit 1, `code: internal`, message naming `SQLITE_READONLY_DIRECTORY`) and nothing is created. A database older than the supported schema is not migrated by a read-only command: it is refused (exit 1, `code: internal`) with a message to run a mutating command (such as `poll`) first. Mutating commands (`watch add`, `watch remove`, `label add`, `label remove`, `poll`, `prune`) create them. SQLite settings, per connection: `busy_timeout` 5000 ms, `journal_size_limit` 64 MiB, `synchronous=FULL`, `foreign_keys=ON`, `trusted_schema=OFF`, `wal_checkpoint(TRUNCATE)` at the end of `poll` and `prune`; queries are parameterized. XDG variables are respected; macOS uses the same paths.

## Labels

Design guide section 9 applies to watches: repeated `--label key=value` on `watch add`, `label add` and `label remove`, a stored set owned by the (watch, owner) pair that added each label (Watches, owners and members), returned verbatim in `--json`, filtered with repeatable `--label` (AND). A PR's labels on an event are the union over its watches at detection time. No key has built-in meaning. The design guide's label multiset is replaced by sets per (watch, owner); `label remove` by one owner does not remove a label another owner holds. Convention for consumers: label your watches with a key that names you (for example `consumer=review-respond`), so one `events --label` call selects your PRs, and a consumer's labels vanish with its reference.

## Consumer notes

- Events are edge-triggered hints, not state: they can be late (up to `full_every` cycles), absent (at-most-once hooks, incomplete parts, the comments, reviews and CI of a reopened PR), duplicated across a store reset, and never authorization. Readiness changes with no event (a thread resolved, `blocked_by`, `mergeable`, a base moved, a withdrawn approval, a late GitLab approval) mean a consumer that merges or notifies on readiness re-reads forgectl `show` and re-evaluates on a schedule as well as on `approved`, `ci`, `ready` and `pushed`, and pins the head sha it evaluated (`--expected-head`).
- First run: on a fresh store take the `cursor` from the first `watch add` result; on a store that already has data take the head from `events` (no `--since`). Existing comments and reviews at first sight never produce events, so a consumer reads current state through forgectl; a consumer keeps a set of handled comment ids (ids are unordered; no watermark).
- A PR's activity before its first snapshot is not an event; a PR opened and commented on within one interval is baselined with the comment already seen. A PR opened while a query watch watched emits `opened`, and its comments at that first snapshot are still baselined.
- `opened` and `reopened` exist from 1.x (Events). Not events: a PR opened before the watch (a PR whose row expired or was dropped and that rejoins emits no second `opened` while its earlier events are retained), or one that newly matches a watch, a PR retargeted or renamed, a review requested, a PR moved back to draft, an approval withdrawn or a review dismissed, a PR becoming unreachable or recovering (`post-poll` names newly unreachable PRs), a mergeability or readiness change. Consumers re-read forgectl.
- `pr` on an event is as of detection; match on `pr_id`. `author` and `reviewer` carry `id` (compare ids, else logins case-insensitively). `is_bot: null` is not a human.
- A fresh `last_poll_finished_at` does not mean every host or PR was observed (a paused host, per-PR failures and `truncated` all exit 0): before treating silence as quiet, read per-host `paused_until` and `last_enumerated_at` and the PRs' `status` and `failure_count` in `list`.
- `watch remove` is idempotent. A re-added expired PR can emit `merged` again.
- `poll --pr` under `already_running` did not refresh the PR (`polled: false`); `events` and `list` carry `last_poll_finished_at`.
- Hook recipe: route only `type`, `pr`, `pr_id`, `repo`, ids and shas into notifications; never author, path or check names. Map type to a notification level (`merged` info, `closed` info, `approved` info, `changes_requested` warn, `ci` warn when `to` is `failing` else info, `pushed` info, `ready` info, `opened` info, `reopened` info, comments info); build the link from `repo` and `pr` with your own host table (GitHub `https://<host>/<owner>/<repo>/pull/<N>`, GitLab `https://<host>/<path>/-/merge_requests/<N>`), or read it from forgectl; events carry no `backend`.
- A hook-wired consumer that must not miss a comment, push or approval also reads `events` with its cursor; the hook is an early nudge (hooks are at-most-once and capped).
- A reopened PR emits `reopened`, and `pushed` if its head changed, and nothing else; read comments, reviews and CI through forgectl when `baselined_at` changes.
- Labels and owners select, they do not authenticate: a consumer acts on a PR only if its own records name it; an event does not say who authored the PR (read it through forgectl).
- Silent baselines: keep `(pr_id, baselined_at)`; when a `pr_id` is new or its `baselined_at` changed (first sight, a reopen, a late part baseline) read comments, reviews and CI through forgectl for that PR and add the ids to your handled set.
- An author that cannot be identified (`author.id` and `login` null) is neither own nor eligible: notify only.
- After `gap` with a different `store_id` every watch is lost: re-add your watches first, then reset your cursor, then re-read your PRs.
- A comment named by an event can be deleted or edited before you fetch it: missing in forgectl means handled.
- `watch.labels` is the union over owners; label your own watches with a key that names you.
- A query watch is ready when `enumerated_at` is non-null and `pending_baseline` is 0. The `cursor` of a `watch add` result is for a consumer that has no stored cursor; one that holds a cursor ignores it.

## Upgrades

- Migrations are additive and run on first use; a database written by a newer version is refused (exit 12, `code: store_too_new`, naming the versions) rather than read. `PRAGMA user_version` mirrors `meta.schema_version`: the larger of the two above the supported version is `store_too_new`, a lower mismatch is refused as corrupt. Before anything is written, a file that is not empty must hold the pr-watch `meta` (with `store_id` and `schema_version`) and `events` tables, else it is refused untouched (a foreign database is never adopted or switched to WAL). A corrupt, non-SQLite or foreign database and a database busy beyond the timeout are reported as `internal` (exit 1); an empty or 0-byte `state.db` is initialized by a command that writes (a read-only command treats it as an empty store and leaves it alone). A database that is current is opened without the write lock, so read-only commands do not wait for a commit.
- `--json` outputs and hook payloads follow semver; new fields are additive (consumers ignore unknown fields). A new event type is a minor change; consumers must ignore types they do not know (`opened` and `reopened` came in 1.x, with their `on-opened` and `on-reopened` hooks; the poll report's `events` object gains the two keys, always present, first).
- A new forgectl minimum is a minor change recorded in the changelog and `MIN_FORGECTL`.
- A deleted or recreated `state.db` creates a new `store_id` (every cursor reports `gap` once). A restored backup keeps its old `store_id`: cursors beyond its head report `gap`, but a consumer whose cursor is below the restored head and which already saw later events can miss events; this is a residual risk, so a restore should be followed by consumers re-syncing.

## Residual risks

- **Late detection.** A change the cheap trigger cannot see (CI completion, GitLab approvals) is found by the unsettled rule or the full pass, up to `poll.full_every` cycles late (about 30 minutes at the defaults on GitHub, an hour on GitLab).
- **At-most-once hooks.** A killed poll leaves stored events whose hooks never ran; a SIGKILL of the poll loses queued hooks; a skipped hook is logged (Hooks, Cap).
- **Hook process escape.** Only the hook's leader process is bounded. A descendant that outlives the leader is neither bounded nor killed, whether it stays in the hook's process group (a plain `cmd &` that survives the leader's normal exit: pr-watch signals the group only at a timeout or a shutdown, never after a normal exit) or leaves it (`setsid`, a double fork into a new session); pr-watch does not wait for it and it outlives the poll. Hook authors must not do this.
- **GitLab approvals.** `approvals_at_head` is `null` (unknown) where the project does not reset approvals on push; an `approved` event there says nothing about the head. GitLab transition shapes for new notes, new checks and head changes were not observed live in the design spikes (the server was quiet) and are a `live` regression item.
- **Enumeration limits.** GitHub search caps at 1000 results and, for a search not scoped to one repository, GitHub may search only a limited number of repositories so results beyond them can be missed while `complete` is true (forgectl's UNVERIFIED risk); a query watch can therefore miss an open PR; `list` prints `last_enumerated_at` per host. A query watch narrowed with `--repo` to a repo that is later renamed or deleted finds no members, and its existing members reach `left_count` 2 after two listings and are snapshotted once; an open one that no longer matches is dropped from the query. A per-PR repo scope whose first listing is wide (the watermark starts at a quiet PR's `updated_at`) costs up to 10 requests once.
- **Clock drift.** No enumeration uses the local clock; a host clock jump is the host's problem.
- **Edits are invisible.** An edited or deleted comment is not an event; a minimized comment stays in `seen`.
- **Reopen.** A closed PR that is reopened is re-baselined: comments, approvals and CI changes while it was closed are not reported (`reopened` and a changed head, `pushed`, are reported), and a PR reopened after `expiry.after_terminal` re-enters as a new baseline and emits no `opened` (its earlier events are retained, `retention.events` permitting; after they are pruned it can emit `opened` once more if created after the watch). A merged PR is final.
- **Large snapshots.** The snapshot call is body-free (`--no-bodies`), so a PR padded with long comments or reviews still produces every event. pr-watch still reads at most `forgectl.max_output_mib` (default 32) MiB from one forgectl call and kills that child's group above it (`too_large`, counted toward `unreachable` unless the fallback finds it terminal or its `show` fails with a code of its own). What can still reach the cap is output that no flag removes: the PR's own `body`, a very long title or an extreme count of comments, reviews or checks (forgectl does not cap its output). For such a PR pr-watch calls `forgectl show <pr>` and detects only `merged` and `closed` (Failures); every other event is absent while it stays over the cap (visible as `last_failure_code: too_large` and `unreachable`). The read cap, not the flag, bounds memory: the in-flight bytes are the sum over hosts of that host's pool size, each worker holding up to the cap plus its parse, about one to two times the bytes (measured: 31 MiB of comments cost about 63 MiB extra to parse), so a worker peaks near 100 MiB at the default cap and the default pools (GitHub 4, GitLab 2) are about 600 MiB in the worst case; a body-free snapshot is typically far below the cap, so this is a bound and not the usual size; size the pools and the cap for it.
- **Persistent incomplete parts.** A part forgectl cannot list completely never produces events (Digest); the condition is visible in `list`, `show`, the report and `log.jsonl`.
- **Unreachable rows are permanent.** An `unreachable` PR never expires by itself (a deleted repo stays visible until its watch is removed, `list --status unreachable` shows it, and `post-poll` named it once); it costs one snapshot per full pass.
- **Silent baselines.** First sight, a reopen and a late part baseline drop activity without an event; `baselined_at` marks them.
- **Early green.** `passing` can be an early green: it does not say every expected check registered (Events).
- **Repo rename.** A repo rename changes `pr` on later events; consumers key on `pr_id` (agent-spawn `pr=` labels hold the `pr` string and must be refreshed by the consumer). GitHub can reuse a renamed repo's old name for another repo; a stale name never authorizes anything. From the rename to the next full pass the cheap trigger may be blind for the renamed repo's per-PR PRs (a listing of the old name can return nothing); detection runs at full-pass cadence until the first snapshot refreshes `repo`.
- **Restore of a backup** (Upgrades) can lose events for a consumer that was ahead of the backup.
- **Same-user processes** can read and edit `state.db`; the event stream is not tamper-proof.
- **forgectl as a boundary.** pr-watch trusts forgectl's sanitizing of one-line text and its classification of failures; a forgectl bug that returns unsanitized text would reach event payloads (the schemas bound the length of every text field to 256 characters).

## Platform notes

Linux, WSL and macOS behave the same; nothing here depends on tmux, inotify or a notifier. cron needs `forgectl` on its `PATH` (`cron install` writes the directory when it is safe). WSL: keep the state dir on the Linux filesystem, not under `/mnt/c`.
